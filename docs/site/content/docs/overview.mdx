<Audience>Everyone</Audience>

Instrument data tends to stay where it was made. Files sit on the PC wired to the plate reader, named by whoever was at the bench, backed up if someone remembers. Finding a result from three months ago means knowing which machine made it and who was running it.

Data Hub moves that data off the instrument PC automatically. A small program called a watcher runs on each instrument PC, watches the folder the instrument saves to, uploads new files as they appear, and groups them into runs. From then on the data is searchable in a browser and reachable from a script or an AI assistant, without anyone copying files to a shared drive. Whoever ran a run can claim it, so their name stays on it.

## What Data Hub isn’t [#what-data-hub-isnt]

Data Hub stores and shows instrument data. It doesn’t do these four things:

- **Change raw files**: uploads are exact copies, and processing only adds new files next to them
- **Replace your lab notebook**: each run has a comment thread for notes and can link to the notebook pages where the experiment is written up
- **Analyze data**: Data Hub reads vendor formats into something you can view and download, and the analysis is still yours
- **Run on the instrument**: processing happens on the server after upload, so nothing competes with the acquisition software for the PC’s resources

## How a file becomes a run [#how-a-file-becomes-a-run]

1. A [watcher](/docs/concepts#watcher) on the instrument PC notices a new file in the folder it’s watching, waits for the file to stop changing, and groups it with the other files from the same acquisition into a [run](/docs/concepts#run).
2. The watcher uploads those files to cloud storage. For [supported instrument types](/docs/instrument-preprocessing), server-side code then reads the vendor’s format, pulls out settings like wavelength or imaging mode, and builds viewable versions such as plate maps or contrast-adjusted images.
3. The run appears in the web app, the REST API, and the Model Context Protocol (MCP) endpoint at the same time, because all three read the same record.

The full picture, including where each piece runs, is in [Architecture](/docs/architecture).

## Where your data shows up [#where-your-data-shows-up]

These are the web app’s main pages:

- **Home**: every instrument’s recent runs together, with counts for today and this week, the lab notebooks that got a run today, and today’s comments
- **Instruments**: one instrument’s runs, with columns matching what that instrument records, and a status badge that says whether its new files can arrive. Each instrument also has a watcher page for the people who maintain it
- **My activity**: runs you’ve claimed, lab notebooks you own, and comments, so you can find your own work without filtering
- **Lab Notebooks**: each lab notebook’s runs from every instrument, gathered on one page. See [Lab notebooks](/docs/lab-notebooks)
- **Comments**: every run comment by day, which you can filter to your runs or to one instrument. Open it from **View all comments** on Home

To see what has changed in Data Hub recently, open **Changelog** from the account menu.

If a term on those pages is unfamiliar, [Concepts](/docs/concepts) defines it. Start with run, watcher, run status, and instrument type.

## Get at the same data from code [#get-at-the-same-data-from-code]

The runs, files, and comments you see in the web app are also available from a REST API that you can call yourself, and from an MCP endpoint that AI clients call on your behalf. Both read the same records as the web app, so a script sees the same runs you do.

- **REST**: at `/api/v1/` on your deployment’s host. Each deployment publishes an OpenAPI 3.1 document at `/api/v1/openapi.json`, so you can generate a client instead of writing one. See the [API overview](/docs/api)
- **MCP**: at `/mcp/v1`. Add it to Claude Code, Claude Desktop, or Cursor by pasting the URL, and the assistant can search runs, read metadata, and fetch files during a conversation. Clients that support MCP Apps also show the same interactive run reports as the web app. See the [MCP overview](/docs/mcp)

The two sign in differently:

- **REST**: a script sends a [personal access token](/docs/concepts#personal-access-token) that an admin creates in the web app, limited to the scopes it needs. The token acts under its own name, so anything the script does is labeled with the token, not a person
- **MCP**: the AI client opens a browser sign-in and a consent screen, then acts as you with your own permissions. Nobody pastes a credential into the AI client

For example, you can pull every run from an instrument for a batch reanalysis, save the latest run’s archive to disk from a script, or ask an assistant which plates from last week failed processing.

## What’s supported today [#whats-supported-today]

Nine instrument types have a processor, covering plate readers, gel docs, qPCR, TapeStation, FPLC, flatbed plate scanners, ND2 microscopy, DishCam time-lapse photos, and the Unchained Labs Aunty for protein melting temperature and particle size. [Instrument data preprocessing](/docs/instrument-preprocessing) lists what each one extracts.

An instrument without a matching processor still works. Its files upload, and you can search, claim, comment on, and download them, but you get no extracted metadata, badges, or previews. Adding a new instrument type takes code changes, so an engineer has to do it.

## Self-hosted by design [#self-hosted-by-design]

Your team runs Data Hub on its own infrastructure, so raw instrument data and everything made from it stay on systems you control. The source code is open under the MIT license.

An engineer deploys these pieces once:

- The web app, which also serves the API and the MCP endpoint, on Vercel
- A PostgreSQL database for instruments, runs, files, and comments
- Three AWS S3 buckets for raw files, processed files, and download archives
- An AWS Lambda that processes each instrument’s files and builds download archives
- A Google OAuth client, which decides who can sign in

The Google OAuth client allows either only your Google Workspace organization or any Google account. Nothing inside Data Hub can override it, so the engineer makes that choice when deploying, and an admin can’t change it later.

Until those pieces exist, nobody can sign in and no watcher can upload. [Deploy Data Hub](/docs/self-hosting) explains the deployment and links to the step-by-step guides in the repository.

## Getting access [#getting-access]

Sign in with a Google account that your deployment allows. Everyone who signs in can browse instruments, runs, and files, comment on runs, and [send feedback](/docs/send-feedback) about Data Hub. Admins can also confirm instruments, create tokens, make other people admins, and connect Linear and Slack. Only an existing admin can make you an admin. See [Security and permissions](/docs/security#roles) for what each role can do.
