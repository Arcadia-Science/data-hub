<Audience>Everyone</Audience>

After instruments are uploading, the web app is where you find runs and act on them: inspect results, claim work, download files, and leave lab notes. The sections below follow the order you’ll use them in.

## Orient yourself in the app [#find-a-run]

The sidebar and the home page are the two starting points for daily work.

**Home** lists recent runs across instruments, most recent first, with counts for today and this week at the top. The **Runs needing attention** card beside them counts runs whose upload failed, whose processing failed, or whose processing stalled, of any age. When it isn’t zero, choose it to list those runs. Filter by date range, who ran it, and instrument-specific metadata when it’s available, then page through results. Below the runs, Home shows up to four of today’s comments; use the date picker to see comments from a different range.

![Home dashboard with instrument status and recent runs](/images/home.webp)

**Instruments** in the sidebar lists five instruments, and **View all** opens the full list. Each instrument’s page starts with its name and a status badge that says whether new files can arrive; see [Check that new files will arrive](#check-files-will-arrive). Under the name are the folder its watcher reads from and the file patterns it uploads, then a runs table with column filters that match the instrument type (for example wavelengths on a plate reader).

![Plate reader instrument page with the runs table and column filters](/images/plate-reader-runs-table.webp)

**My runs** lists runs you’ve claimed, so you can return to your own work without re-filtering the full dashboard. Its **Runs needing attention** card counts only your runs.

![My runs page listing runs attributed to the signed-in user](/images/my-runs.webp)

**Comments** lists every run comment by day. Open it from **View all comments** on Home. Each person’s profile page also shows the comments they wrote and the comments on runs they ran.

![Comments page listing each run comment by day, with filters for instrument and for comments on your runs](/images/comments-page.webp)

### Narrow a long run list [#narrow-a-long-run-list]

Home and the instrument pages share the same four controls:

- **Search runs**: filters the list by run name as you type
- **Date range**: presets from Today through Last 4 weeks, plus a custom range. Home shows today’s runs until you pick another range, and **All time** shows every run
- **Add filter**: filter by run status, or turn on **Show deleted runs**
- **Column headers**: sort by **Run Started**, **Last Updated**, size, who ran it, or any instrument-specific column

The **Lab Notebook** column header filters the list by [lab notebook](#lab-notebook). Pick **In any lab notebook** or **In no lab notebook**, or pick one of the lab notebooks it lists to see only that lab notebook's runs. Each lab notebook shows how many of the listed runs it holds. Type in the menu's search box to narrow the list.

**Run Started** is when the instrument acquired the run. **Last Updated** changes when the run’s files change, or when someone edits, claims, or comments on it, or adds it to or removes it from a lab notebook. The default order is newest run first. The sort order is saved in the page link, so a link you share opens with the same order.

### What each run status means [#run-status]

A run’s status tells you how far its files have got from the instrument to the dashboard:

| Status | Meaning |
| --- | --- |
| Failed | At least one file failed processing. The file’s row on the run page gives the reason. |
| Stalled | At least one file has been processing for more than 20 minutes without finishing. Reprocess it to try again. |
| Upload failed | The watcher gave up on at least one file, for example because its folder is no longer on the instrument PC. See [When an upload fails](/docs/browse-runs#upload-failed). |
| Waiting to upload | Files are on their way from the instrument PC: someone requested them, or the watcher uploads them on its own. |
| Uploaded | The files are in storage. Processing hasn’t started, or this instrument type has no processor. |
| Queued | You chose **Reprocess**, and the files are waiting for a free processing slot. They start as other files finish. |
| Processing | The server is reading the files, extracting metadata, and building reports. |
| Not uploaded | Some files are only on the instrument PC, and nothing will upload them until someone requests them. Common on instruments in manual upload mode. |
| Completed | Processing finished. |
| Empty | The run has no files. |

A run with files in several states shows the first status in this table that applies. For example, a run with one failed file and nine completed files shows **Failed**, and a run with three processed files and 285 that nobody requested shows **Not uploaded**.

**Waiting to upload** and **Not uploaded** replace the earlier **Pending upload**. A saved link or API call that filters by `pending` still works and matches both.

## Check that new files will arrive [#check-files-will-arrive]

If a file you saved on the instrument PC hasn’t shown up, start with the badge beside the instrument’s name. It says whether new files can reach Data Hub. The same badge appears in the instruments table, on Home, and in search results.

| Badge | What it means |
| --- | --- |
| **Online** | New files upload automatically. For an instrument in manual upload mode, new files upload when someone requests them. |
| **Restarting** | The instrument PC is restarting or updating. This usually takes a minute or two, and you don’t need to do anything. |
| **Connecting** | The watcher was just set up and hasn’t checked in yet. If it hasn’t checked in after 15 minutes, the badge turns **Offline**. |
| **Offline** | New files won’t appear right now. A notice under the instrument’s name says why. |
| **Pending** | An admin hasn’t confirmed this instrument yet. Admins see a card in place of the runs table; members see one line. |
| **Retired** | The instrument no longer takes new runs. Its runs stay browsable. |

Hover over the badge, or focus it with the keyboard, for a short explanation. Select it to open the instrument’s watcher page, where anyone signed in can read its activity, health, and settings. Only admins can change anything there. The watcher is the program on the instrument PC that finds new files and uploads them; [Concepts](/docs/concepts#instrument-status) has the full rules for each badge.

![Instrument page with an Online badge and its explanation in a tooltip](/images/instrument-status-badge.webp)

### When the badge reads Offline [#when-offline]

A red notice sits between the instrument’s name and its runs. It says what happened in plain words:

| Notice | What happened |
| --- | --- |
| **New files aren’t being picked up** | The watcher is running but can’t find its watch folder, which the notice names. An admin can choose **Change folder** to fix it. |
| **The watcher isn’t checking in** | The watcher hasn’t checked in for 5 minutes, or didn’t come back within 15 minutes of a restart. The notice says when it last did. The PC may be off, or the watcher may have crashed. |
| **The watcher never checked in** | The watcher was set up, but no check-in arrived within 15 minutes. Its service may not be running on the PC, or the PC can’t reach Data Hub. |
| **Uploads from this instrument are paused** | Someone stopped the watcher on the PC. New files appear once it’s started again. |
| **This instrument isn’t connected to a watcher** | The instrument never had a watcher, or its watcher was deregistered, which the notice dates and credits. Admins can choose **Connect a watcher**, which opens [Set up an instrument](/docs/set-up-an-instrument). |

**See details** opens the watcher’s **Activity** tab. Members see only that link, and none when there is no watcher to look at. Tell an admin what the notice says, or send them the link: the [troubleshooting guide](/docs/troubleshoot-a-watcher#instrument-shows-offline) covers each reason.

![Instrument page with a red Offline badge and a notice that the watcher can’t find its watch folder, with Change folder and See details](/images/instrument-offline-notice.webp)

An instrument in manual upload mode, whatever its badge says, shows a blue note beside its file patterns: “Files upload when someone requests them.” That isn’t a problem. Files wait until someone chooses **Upload**; see [Request an upload](#request-upload).

## Search the workspace [#search]

Press **⌘&nbsp;K** (macOS) or **Ctrl&nbsp;K** (Windows/Linux) to open global search from any page. Results are grouped into runs, notebooks, files, instruments, users, and comments. That means you can also look up a colleague’s work or the text of a lab note. A file hit opens the parent run with the files table already filtered to that file.

[Lab notebooks](#lab-notebook) match on their name, description, or link. Paste a notebook page’s URL to find its notebook, even when your copy of the link differs from the one saved, then open the notebook to see all of its runs. The arrow beside a notebook opens the notebook itself.

![Global search modal with results for runs and files](/images/search-modal.webp)

## Open a run and inspect results [#open-run-detail]

Each run has a details page at `/instruments/your_instrument_id/runs/your_run_id`. The arrows beside the run name step you to the next or previous run without going back to the list.

The top of the page lists who ran it, the number of raw files, and their total size. Below that, the **Lab Notebooks** section lists the lab notebooks the run is in; see [Add runs to a lab notebook](#lab-notebook). What you see after that depends on the instrument type and whether a processor ran:

- Metadata tags for extracted fields, such as experiment type, wavelength, or temperature
- Processed reports such as tables, images, PDFs, and videos, including interactive plate maps for plate readers and a video player for DishCam runs
- A files table of everything in the run, labeled Raw or Processed, with each file’s size and status

Click a metadata tag to open the instrument’s runs table filtered to that value. For example, clicking a wavelength tag lists every run on that instrument recorded at the same wavelength.

Reports with many images, PDFs, or spectra show one item at a time. Search by filename to jump anywhere in the run, or use the arrows to step through it. The counter beside the arrows shows your position out of the total. Plate maps with more than 12 columns, such as 384-well plates, scroll sideways inside the plate.

Per-type inputs and outputs are in [Instrument data preprocessing](/docs/instrument-preprocessing).

![Gel doc run detail with metadata badges, files table, and report preview](/images/gel-doc-run-details.webp)

### Filter the files table [#filter-files]

The files table has separate **Type** and **Status** filters. Use them to show, for example, only failed files or only processed CSVs. **Download all** and the run archive include only the files the filters show.

### Live file updates [#live-file-updates]

While files are uploading, queued, or processing, the run page checks for updates every 5 seconds for up to 5 minutes. After that it stops and shows **Stopped checking for file updates**. Choose **Refresh** to check for another 5 minutes. Uploading or reprocessing files from the page also starts a new 5 minutes.

## Claim who ran it [#claim-who-ran-it]

Use **Claim** on the run details page to attribute yourself. You can claim or unclaim your own user only, so nobody else can attribute a run to you. Claims show on the run and appear in “ran by” filters on Home and elsewhere. API tokens can’t claim runs; a signed-in person has to.

### Asked after a download [#claim-prompt]

When you download a run archive or a file from a run nobody has claimed, Data Hub asks **Did you run this?** in a card near the bottom of the page. Choose **I ran this** to claim the run, or **Not me** so that browser doesn’t ask about the run again. Downloading several runs from a runs list asks once about all the unclaimed ones, and **I ran these** claims them all.

An AI assistant connected to the [MCP server](/docs/mcp) learns the same thing when it downloads from an unclaimed run, so it can ask you and claim the run for you.

## Add runs to a lab notebook [#lab-notebook]

A lab notebook in Data Hub stands for one lab notebook page, such as a Notion or Google Docs page. Adding a run to it lets whoever analyzes the run read how the experiment was set up, and gathers the lab notebook's runs from every instrument in one place. A run can be in several lab notebooks.

On the run page, choose **Add to lab notebook** in the **Lab Notebooks** section. Type a lab notebook's name to pick one Data Hub already has, or paste the page's link. A link to a page that has no lab notebook yet creates one: give it a name, which starts as a name worked out from the link. For a Notion page, that's its title. Leave **Make me the owner** ticked to own a lab notebook you create this way. Tick **I ran this run** to claim the run at the same time. Each lab notebook shows who added the run. Its name opens the [lab notebook's page](#notebook-page) in Data Hub, and the arrow beside it opens the lab notebook itself. Use its **⋯** menu to copy the lab notebook's link or remove the run from it.

- A run can be in up to 20 lab notebooks.
- Each page has one lab notebook, with one name that every run in it shares. Two links count as the same page when they differ only in `http` or `https`, `www.`, a trailing slash, the part after `#`, or tracking parameters such as `utm_source`. Notion links count as the same page when they have the same page ID, so a link copied before the page was renamed still finds its lab notebook.
- Anyone signed in can add runs to a lab notebook or remove them.
- A deleted run stays in its lab notebooks, but they can't change until the run is restored.
- A deleted lab notebook keeps its runs, and restoring it brings them back. Pasting a deleted lab notebook's link offers to restore it.

Runs tables show each run's first lab notebook in the **Lab Notebook** column, with **+1**, **+2**, and so on when there are more. Filter that column to **In no lab notebook** to find runs that still need one, or to a lab notebook to find all of its runs. To add many runs at once, select them and choose **Add to lab notebook**; see [Act on several runs at once](#bulk-actions).

### A lab notebook's page [#notebook-page]

Each lab notebook has a page in Data Hub that lists its runs from every instrument. Open it from a lab notebook's name anywhere in Data Hub, or from **Lab Notebooks** in the sidebar, which lists the lab notebooks you opened last and the ones that most recently got a run. **View all** opens the list of every lab notebook, with its owner, run count, instruments, and newest run. Search it by name, or paste a lab notebook's link to find its page. Choose **New lab notebook** there to create a lab notebook before it has any runs.

The page shows the lab notebook's description and owner above its runs, which you can search, filter, and act on like any runs table. **Open lab notebook** opens the lab notebook itself. From the **⋯** menu:

- **Edit details** changes the lab notebook's name, description, owner, or link. The name is shared by every run in it. A link can't point to a page that another lab notebook already has.
- **Copy page link** copies the address of the Data Hub page. Paste it into the lab notebook, so the lab notebook and its data point at each other.
- **Delete** takes the lab notebook off its runs and out of lists and search. The page stays, with **Restore**, which brings the lab notebook back with all of its runs.

Select runs on the page and choose **Remove from this lab notebook** to take them out.

### From scripts and AI assistants [#lab-notebook-api]

Scripts manage lab notebooks through the [REST API](/docs/api)'s `/lab-notebooks` endpoints. Listing and reading lab notebooks needs the `runs:read` scope. Creating, editing, deleting, and restoring them, and adding or removing their runs, needs `lab-notebooks:write`. A token that registered a watcher can add or remove only its own instrument's runs, and can't create, edit, delete, or restore lab notebooks. The run lists take `has_lab_notebook` to list runs in any lab notebook or in none, and `lab_notebook_id` to list one lab notebook's runs. Run responses list each run's `lab_notebooks`.

An AI assistant connected to the [MCP server](/docs/mcp) can do the same with the `list_lab_notebooks`, `get_lab_notebook`, `create_lab_notebook`, `update_lab_notebook`, `delete_lab_notebook`, `restore_lab_notebook`, `add_runs_to_lab_notebook`, and `remove_runs_from_lab_notebook` tools. The `search_runs` tool filters by lab notebook with `hasLabNotebook` and `labNotebookId`.

## Download files [#download-files]

From the files table you can:

- Preview a CSV, TSV, JSON, or other text file by clicking its row. The preview shows the first 1 MB of the file. Use the back and forward buttons to move between previewable files on the same page of the table. **Download** in that window saves the file
- Select files and choose **Download** in the bar that appears above the files table. One file downloads directly. Two or more come as a single zip, which builds in the background like **Download all**
- Choose **Download all** to build a zip of active files in the run, with any active file filters applied

![File preview window showing the first rows of a processed CSV, with a Download button and buttons for the next and previous file](/images/csv-preview.webp)

Large zips build in the background. When one isn’t ready yet, Data Hub tells you how long to wait before trying again.

## Act on several runs at once [#bulk-actions]

Select the checkbox on one or more run rows to open an action bar at the bottom of the list. Run rows have no buttons of their own; every run action goes through this bar.

- **I ran these**: claim every selected run in one step
- **Remove my attribution**: unclaim them
- **Upload**: ask the watcher to upload files that are still on the instrument PC. Data Hub refuses the request for a run whose instrument isn’t **Online** or **Restarting**, and a message says how many failed; see [Request an upload](#request-upload)
- **Download**: download a zip of each selected run
- **Reprocess**: run server-side processing again, including on runs whose files have stalled
- **Add to lab notebook**: add every selected run to the same [lab notebook](#lab-notebook). Runs already in it are skipped
- **Remove from lab notebook**: choose from the lab notebooks the selected runs are in, and remove every selected run from them
- **Delete**: mark the selected runs deleted

**Upload**, **Download**, **Reprocess**, **Delete**, and the lab notebook actions appear only when every selected run allows them. For example, **Reprocess** is hidden if one of the selected runs belongs to an instrument type with no processor, and the lab notebook actions are hidden if a selected run is deleted. **Remove from lab notebook** also needs at least one selected run to be in a lab notebook. The lab notebook actions work on up to 100 runs at a time. The checkbox in the header row selects every run on the page, and **Clear** drops the selection.

The selection stays when you move to another page of the same results. It clears when you change the search, a filter, or the sort, so the bar never acts on runs from a list you are no longer looking at.

The files table on a run page works the same way: select files to get **Upload**, **Dismiss**, **Reprocess**, and **Download** for just those files. Its **Upload** follows the instrument’s badge, like the other [Upload buttons](#request-upload). Its selection also clears when you change the files search, a filter, or the sort.

![Run list with several runs selected and the bulk action bar open](/images/bulk-actions.webp)

## Comment on a run [#comment]

The comments thread on run details is for lab notes and follow-ups. Comment activity can notify people who claimed the run or already commented, and clicking a comment notification scrolls to that comment. Set preferences under **Settings → Notifications**; see [Configure notifications](/docs/configure-notifications).

Only the author of a comment can edit it. Authors can delete their own comments, and workspace admins can delete any comment. Comments posted by a script through an API token show the token’s name with a key icon instead of a person.

## Reprocess or delete a run [#reprocess-and-delete]

Reprocessing runs server-side processing again. Use it after a file failed or stalled, or after an engineer fixes the code that reads a file type. The stored result doesn’t change until you reprocess.

- On the run page, hover over a file and choose **Reprocess**.
- To reprocess several files, select them in the files table and choose **Reprocess** in the bar.
- To reprocess whole runs, select them in a run list and choose **Reprocess** in the bar.

Reprocessing sends only the original instrument files. Files Data Hub generated, such as videos, previews, and CSVs, have no **Reprocess** button and are rebuilt from the originals. Reprocessed files go through a queue; see [How reprocessing is queued](/docs/browse-runs#reprocess-queue).

**Delete** marks the run deleted without removing stored files. To find a deleted run again, turn on **Show deleted runs** under **Add filter**, then open it and choose **Restore**. Anyone signed in can delete or restore a run. Files that were queued for reprocessing when the run was deleted stay queued and don’t start while the run is deleted. If you restore the run, they start as processing slots free up.

Deleting a run also cancels the uploads that were requested for its files, so the watcher stops trying to send them. Those files go back to **Not uploaded**. Restoring the run doesn’t bring the requests back. Choose **Upload** again if you still want the files. See [Request an upload](/docs/browse-runs#request-upload).

While a run is deleted, Data Hub refuses a watcher’s reports of it, so the watcher’s new files aren’t added. After you restore the run, restart the watcher to send them, or choose **Upload** on a file to have the watcher send that file without a restart. Watchers before 1.4.3 also send them when another file of the run finishes. See [A run was deleted on Data Hub](/docs/troubleshoot-a-watcher#a-run-was-deleted-on-data-hub).

![Deleted run page with a red banner naming who deleted it and when, and a Restore button](/images/deleted-run.webp)

### How reprocessing is queued [#reprocess-queue]

Reprocessing starts at most 10 files at a time, counted across all runs and instruments. When you choose **Reprocess**, each file goes into a queue:

- A file that can start right away shows **Processing**.
- A file that has to wait shows **Queued**. It starts when another file finishes, and files that were queued earlier start first.
- A run with queued files shows **Queued** in the runs list, unless a file in it failed, stalled, couldn’t upload, is waiting to upload, or is uploaded and not yet processing.
- If Data Hub can’t send a file to the processor, or the processor ends with an error without saving a result, the file shows **Failed** with a message that says so, and the next queued file starts. Reprocess the failed file to try again.
- To take the waiting files out of the queue, choose **Cancel queued** at the top of the run page. Each queued file shows **Failed** with a message that says the reprocess was cancelled, and you can reprocess it again. Files that have already started aren’t affected.

Files that arrive from a watcher upload count toward the 10, but they start right away and never wait in the queue. A file that has been processing for more than 20 minutes without finishing stops counting, so one stuck file doesn’t hold up the queue.

A large run takes several rounds. For example, reprocessing a run of 80 files starts 10 files, and the other 70 show **Queued** until slots open. You can leave the page, because the queue keeps running. A queued file has no **Reprocess** button. An admin who runs Data Hub can change the limit with the `PROCESSING_CONCURRENCY_LIMIT` variable; see the [web application environment variables](https://github.com/Arcadia-Science/data-hub/blob/production/docs/developer/getting-started.md#web-application).

If a file that the queue started never finishes, for example because Data Hub restarted just as it started the file, it shows **Stalled** after 20 minutes. The queue then puts it back in line once. If it stalls a second time, it stays **Stalled** until you reprocess it.

### Request an upload [#request-upload]

A file that the watcher found but nobody requested reads **Not uploaded**. Choose **Upload** on that file to ask the watcher to send it, or **Upload all** at the top of the **Files** section to ask for every file in the run that is **Not uploaded** or **Upload failed**. A requested file reads **Uploading** until it arrives, and the watcher picks up the request within a minute. On instruments that upload automatically, this needs watcher 1.2.1 or later; see [Roll out watcher releases](/docs/watcher-releases#what-each-version-adds). The footer under the files table counts how many files are waiting on the instrument PC, how many couldn’t upload, and how many are uploaded.

On an instrument that uploads automatically, a new file reads **Waiting to upload** until the watcher sends it. This needs watcher 1.4.5 or later; with an older watcher the file reads **Not uploaded** for the minute or two before it arrives.

The **Upload** and **Upload all** buttons on a run page follow the instrument’s badge. When one is turned off, the reason shows beside it:

| Badge | Upload buttons | Beside them |
| --- | --- | --- |
| **Online** | On | Nothing |
| **Restarting** | On. Requests wait until the watcher is back | “The instrument PC is restarting. Uploads start once it’s back.” |
| **Connecting** | Off | “The watcher hasn’t checked in yet.” |
| **Offline** | Off | “Can’t upload while the watcher is offline.” |
| **Pending** | Off | “This instrument is waiting for an admin to confirm it.” |
| **Retired** | Off | “This instrument is retired.” |

If the badge reads **Offline** and the run has files that are still on the instrument PC, a red notice sits above the **Files** section. It says how many files are still on the PC, which watcher isn’t running, and when it last checked in, and links to **See details**. A run with no waiting files never shows the notice, whatever the badge says.

![Run page for an offline instrument, with a notice that four files are still on the instrument PC and a turned-off Upload all button with the reason beside it](/images/run-offline-notice.webp)

Data Hub keeps a request made while the instrument is **Restarting** and the watcher uploads the files once it’s back. If no heartbeat arrives for about 15 minutes, Data Hub cancels the request and the files read **Not uploaded** again.

The **Upload** button on a runs list doesn’t follow the badge. Select runs and choose it to ask for every waiting file in them. For an instrument that is **Offline**, **Connecting**, **Pending**, or **Retired**, Data Hub refuses that run’s request, and a message reports how many runs failed. Choose **Upload** from the run page instead to see why.

For instruments in [manual upload mode](/docs/concepts#upload-mode), every file waits for this approval. **Dismiss** tells the watcher not to upload a file. See [Manage the watcher fleet](/docs/manage-watchers#approving-manual-uploads).

### When an upload fails [#upload-failed]

The watcher gives up on a file when it can’t send it. The file then reads **Upload failed**, and hovering over the status shows why:

- **The folder is no longer on the instrument PC.** Someone renamed or moved the run’s folder after the watcher found it. The files under the new name usually arrive as a new run, so look for a run with the same start time and a similar name.
- **The file isn’t on the instrument PC.** The folder is there but the file was moved or deleted.
- **The upload kept failing.** The watcher tried and the upload failed each time, usually a network problem. The message shows the last error.
- **The path is outside the watch folder.** The watcher won’t upload a file outside the folder it watches.

For a requested file, the watcher checks three times, about a minute apart, before it gives up. On an instrument that uploads automatically, it gives up as soon as an upload fails, and it tries again the next time it starts.

A red notice above the **Files** section lists the files that couldn’t upload, one block per reason and folder. Each block says why and when the watcher gave up. Once the cause is fixed on the PC, choose **Upload again** in the block, or **Upload** on a single file, to try again. If the files are gone for good, choose **Dismiss these files**. The run reads **Upload failed** until every such file is uploaded or dismissed, and the watcher’s activity shows one “Couldn’t upload” entry per run and reason.

Whoever requested the files gets one notification per run and reason, in the app and, if they connected Slack, as a direct message. See [Configure notifications](/docs/configure-notifications).

Marking files **Upload failed** needs watcher 1.4.5 or later. An older watcher puts the file back to **Not uploaded** instead, without a reason; see [Roll out watcher releases](/docs/watcher-releases#what-each-version-adds).

## Use the same data outside the UI [#programmatic-access]

You can also list and fetch the same runs and files over the [REST API](/docs/api) or the [Model Context Protocol (MCP) endpoint](/docs/mcp). REST needs a [personal access token](/docs/concepts#personal-access-token); scopes and creation are covered in [Issue and revoke tokens](/docs/manage-tokens). MCP clients sign in through the browser instead, and clients that support MCP Apps show the same interactive run report you see here.
