<Audience>Everyone</Audience>

Once instruments are uploading, use the web app to find runs and work with them: read results, claim your runs, download files, and leave lab notes. Lab notebooks have their own page, [Lab notebooks](/docs/lab-notebooks).

## Orient yourself in the app [#find-a-run]

The sidebar and the home page are the two starting points for daily work.

**Home** lists recent runs across instruments, newest first, with counts for today and this week at the top. Filter by date range, who ran it, and instrument-specific metadata when it’s available, then page through the results. Below the runs, Home shows up to four of today’s comments; use the date picker to see comments from another range.

The **Runs needing attention** card beside the counts shows how many runs, of any age, failed to upload, failed processing, or stalled. When it isn’t zero, choose it to list those runs.

![Home page with instrument status and recent runs](/images/home.webp)

**Instruments** in the sidebar lists five instruments, and **View all** opens the full list. Each instrument’s page starts with its name and a status badge that says whether new files can arrive; see [Check that new files will arrive](#check-files-will-arrive). Under the name are the folder its watcher reads from and the file patterns it uploads, then a runs table with column filters that match the instrument type (for example wavelengths on a plate reader).

![Plate reader instrument page with the runs table and column filters](/images/plate-reader-runs-table.webp)

**My runs** lists runs you’ve claimed, so you can return to your own work without filtering every run. Its **Runs needing attention** card counts only your runs.

![My runs page listing runs attributed to the signed-in user](/images/my-runs.webp)

**Comments** lists every run comment by day. Open it from **View all comments** on Home. Each person’s profile page also shows the comments they wrote and the comments on runs they ran.

![Comments page listing each run comment by day, with filters for instrument and for comments on your runs](/images/comments-page.webp)

### Narrow a long run list [#narrow-a-long-run-list]

Home and the instrument pages share the same four controls:

- **Search runs**: filters the list by run name as you type
- **Date range**: presets from Today through Last 4 weeks, plus a custom range. Home shows today’s runs until you pick another range, and **All time** shows every run
- **Add filter**: filter by run status, or turn on **Show deleted runs**
- **Column headers**: sort by **Run Started**, **Last Updated**, size, who ran it, or any instrument-specific column

The **Lab Notebook** column header filters the list by lab notebook, or to runs in none; see [Find runs by lab notebook](/docs/lab-notebooks#find-runs).

**Run Started** is when the instrument acquired the run. **Last Updated** changes when the run’s files change, or when someone edits, claims, or comments on it, or adds it to or removes it from a lab notebook. The default order is newest run first. The sort order is saved in the page link, so a link you share opens with the same order.

### What each run status means [#run-status]

A run’s status tells you how far its files have got from the instrument to the web app:

| Status | Meaning |
| --- | --- |
| Failed | At least one file failed processing. The file’s row on the run page gives the reason. |
| Stalled | At least one file has been processing for more than 20 minutes without finishing. Reprocess it to try again. |
| Upload failed | The watcher gave up on at least one file, for example because its folder is no longer on the instrument PC. See [When an upload fails](#upload-failed). |
| Waiting to upload | Files are on their way from the instrument PC: someone requested them, or the watcher uploads them on its own. |
| Uploaded | The files are in storage. Processing hasn’t started, or this instrument type has no processor. |
| Queued | You chose **Reprocess**, and the files are waiting for a free processing slot. They start as other files finish. |
| Processing | The server is reading the files, extracting metadata, and building reports. |
| Not uploaded | Some files are only on the instrument PC, and nothing will upload them until someone requests them. Common on instruments in manual upload mode. |
| Completed | Processing finished. |
| Empty | The run has no files. |

A run with files in several states shows the first status in this table that applies. For example, a run with one failed file and nine completed files shows **Failed**, and a run with three processed files and 285 that nobody requested shows **Not uploaded**.

**Waiting to upload** and **Not uploaded** replace the earlier **Pending upload**. A saved link or API call that filters by `pending` still works and matches both.

## Check that new files will arrive [#check-files-will-arrive]

If a file you saved on the instrument PC hasn’t shown up, start with the badge beside the instrument’s name. It says whether new files can reach Data Hub. The same badge appears in the instruments table, on Home, and in search results.

| Badge | What it means |
| --- | --- |
| **Online** | New files upload automatically. For an instrument in manual upload mode, new files upload when someone requests them. |
| **Restarting** | The instrument PC is restarting or the watcher is updating. Either takes a minute or two, and you don’t need to do anything. |
| **Connecting** | The watcher was set up recently and hasn’t checked in yet. If it hasn’t checked in after 15 minutes, the badge turns **Offline**. |
| **Offline** | New files won’t appear right now. A notice under the instrument’s name says why. |
| **Pending** | An admin hasn’t confirmed this instrument yet. Admins see a card in place of the runs table; members see one line. |
| **Retired** | The instrument no longer takes new runs. Its runs stay browsable. |

Hover over the badge, or focus it with the keyboard, for a short explanation. [Concepts](/docs/concepts#instrument-status) has the full rules for each badge.

Select the badge to open the instrument’s watcher page. The watcher is the program on the instrument PC that finds new files and uploads them. Anyone signed in can read its activity, health, and settings there, and only admins can change them.

![Instrument page with an Online badge and its explanation in a tooltip](/images/instrument-status-badge.webp)

### When the badge reads Offline [#when-offline]

A red notice between the instrument’s name and its runs says what happened:

| Notice | What happened |
| --- | --- |
| **New files aren’t being picked up** | The watcher is running but can’t find its watch folder, which the notice names. An admin can choose **Change folder** to fix it. |
| **The watcher isn’t checking in** | The watcher hasn’t checked in for 5 minutes, or didn’t come back within 15 minutes of a restart. The notice says when it last did. The PC may be off, or the watcher may have crashed. |
| **The watcher never checked in** | The watcher was set up, but no check-in arrived within 15 minutes. Its service may not be running on the PC, or the PC can’t reach Data Hub. |
| **Uploads from this instrument are paused** | Someone stopped the watcher on the PC. New files appear once it’s started again. |
| **This instrument isn’t connected to a watcher** | The instrument never had a watcher, or its watcher was deregistered, which the notice dates and credits. Admins can choose **Connect a watcher**, which opens [Set up an instrument](/docs/set-up-an-instrument). |

**See details** opens the watcher’s **Activity** tab. Members see only that link, or no link when there’s no watcher. To get it fixed, tell an admin what the notice says or send them the link. [Troubleshoot a watcher](/docs/troubleshoot-a-watcher#instrument-shows-offline) covers each reason.

![Instrument page with a red Offline badge and a notice that the watcher can’t find its watch folder, with Change folder and See details](/images/instrument-offline-notice.webp)

An instrument in manual upload mode, whatever its badge says, shows a blue note beside its file patterns: “Files upload when someone requests them.” That isn’t a problem. Files wait until someone chooses **Upload**; see [Request an upload](#request-upload).

## Search the workspace [#search]

Press **⌘&nbsp;K** (macOS) or **Ctrl&nbsp;K** (Windows/Linux) to open global search from any page. Results are grouped into runs, lab notebooks, files, instruments, users, and comments, so you can also look up a colleague’s work or the text of a lab note. Selecting a file opens its run with the files table filtered to that file. Lab notebooks match on their name, description, or notebook page link; see [Find runs by lab notebook](/docs/lab-notebooks#find-runs).

![Global search modal with results for runs and files](/images/search-modal.webp)

## Open a run and inspect results [#open-run-detail]

Each run has a page at `/instruments/your_instrument_id/runs/your_run_id`. The arrows beside the run name step you to the next or previous run without going back to the list.

The top of the page lists who ran it, the number of raw files, and their total size. Below that, the **Lab Notebooks** section lists the lab notebooks the run is in; see [Lab notebooks](/docs/lab-notebooks#add-runs). What you see after that depends on the instrument type and whether a processor ran:

- Metadata tags for extracted fields, such as experiment type, wavelength, or temperature
- Processed reports such as tables, images, PDFs, and videos, including interactive plate maps for plate readers and a video player for DishCam runs
- A files table of everything in the run, labeled Raw or Processed, with each file’s size and status

Select a metadata tag to open the instrument’s runs table filtered to that value. For example, selecting a wavelength tag lists every run on that instrument recorded at the same wavelength.

Reports with many images, PDFs, or spectra show one item at a time. Search by filename to jump anywhere in the run, or use the arrows to step through it. The counter beside the arrows shows your position out of the total. Plate maps with more than 12 columns, such as 384-well plates, scroll sideways inside the plate.

Per-type inputs and outputs are in [Instrument data preprocessing](/docs/instrument-preprocessing).

![Gel doc run detail with metadata badges, files table, and report preview](/images/gel-doc-run-details.webp)

### Search, filter, and sort the files table [#filter-files]

Type in **Search files** to find files by name. Choose **Add filter** to narrow the table by **Type**, which is **Raw** or **Processed**, or by **Status**. Use them to show, for example, only failed files or only processed CSVs. A number on the button says how many filters are on.

**Show deleted files**, at the top of the same menu, lists the run’s deleted files too, with how many match your search and filters. A status filter never lists a deleted file, even one that was completed before it was deleted.

To sort, choose a column heading (**File name**, **Size**, **Created**, or **Status**) and then **Sort ascending** or **Sort descending**. The table starts sorted by file name, A to Z. Raw and processed files sort together in one list. The arrow beside a heading shows which column the table is sorted by, and in which direction.

The search, filters, and sort are part of the page’s address, so you can send someone a link to the table as you see it. With a search or filter on, **Download all** becomes **Download filtered**, and its zip holds only the files they show. A deleted file is never in it.

### Live file updates [#live-file-updates]

While files are uploading, queued, or processing, the run page checks for updates every 5 seconds for up to 5 minutes. After that it stops and shows **Stopped checking for file updates**. Choose **Refresh** to check for another 5 minutes. Uploading or reprocessing files from the page also starts a new 5 minutes.

## Claim who ran it [#claim-who-ran-it]

Choose **Claim** on the run page to put your name on the run. You can only claim or unclaim a run for yourself, so nobody else can put your name on a run. Your claim shows on the run and in the “ran by” filters. API tokens can’t claim runs; a signed-in person has to.

### Asked after a download [#claim-prompt]

When you download a run archive or a file from a run nobody has claimed, Data Hub asks **Did you run this?** in a card near the bottom of the page. Choose **I ran this** to claim the run, or **Not me** so this browser doesn’t ask about the run again. Downloading several runs from a runs list asks once about all the unclaimed ones, and **I ran these** claims them all.

An AI assistant connected to the [MCP server](/docs/mcp) is told when it downloads from an unclaimed run, so it can ask you and claim the run for you.

## Add runs to a lab notebook [#lab-notebook]

A lab notebook gathers the runs behind one notebook page, such as a Notion or Google Docs page, from every instrument. On a run page, choose **Add to lab notebook** in the **Lab Notebooks** section. To add several runs at once, select them in a runs list and choose **Add to lab notebook** in the action bar. [Lab notebooks](/docs/lab-notebooks) covers adding runs, finding them, and each lab notebook’s page.

## Download files [#download-files]

From the files table you can:

- Open any file by selecting its row, anywhere except the checkbox. A CSV, TSV, JSON, or other text file shows its first 1 MB. Any other file says it can’t be previewed there, and a file that hasn’t reached Data Hub yet says so. The back and forward buttons step through the files on the same page of the table, in the order the table shows them. **Download** in that window saves the file
- Select files and choose **Download** in the bar at the bottom of the window. One file downloads directly. Two or more come as a single zip, which builds in the background like **Download all**
- Choose **Download all** to build a zip of the run's files, or **Download filtered** when a search or filter is on. Deleted files are left out

![File preview window showing the first rows of a processed CSV, with a Download button and buttons for the next and previous file](/images/csv-preview.webp)

Large zips build in the background. When one isn’t ready yet, Data Hub tells you how long to wait before trying again.

## Act on several runs at once [#bulk-actions]

Select the checkbox on one or more run rows to open an action bar at the bottom of the list. Run rows have no buttons of their own; every run action goes through this bar.

- **I ran these**: claim every selected run in one step
- **Remove my attribution**: unclaim them
- **Upload**: ask the watcher to upload files that are still on the instrument PC. Data Hub refuses the request for a run whose instrument isn’t **Online** or **Restarting**, and a message says how many failed; see [Request an upload](#request-upload)
- **Download**: download a zip of each selected run
- **Reprocess**: run server-side processing again, including on runs whose files have stalled
- **Add to lab notebook**: add every selected run to the same [lab notebook](/docs/lab-notebooks). Runs already in it are skipped
- **Remove from lab notebook**: choose from the lab notebooks the selected runs are in, and remove every selected run from them
- **Delete**: mark the selected runs deleted

**Upload**, **Download**, **Reprocess**, **Delete**, and the lab notebook actions appear only when every selected run allows them. For example, **Reprocess** is hidden if one of the selected runs belongs to an instrument type with no processor, and the lab notebook actions are hidden if a selected run is deleted. **Remove from lab notebook** also needs at least one selected run to be in a lab notebook, and the lab notebook actions work on up to 100 runs at a time.

The checkbox in the header row selects every run on the page, and **Clear** drops the selection.

The selection stays when you move to another page of the same results. It clears when you change the search, a filter, or the sort, so the bar never acts on runs from a list you are no longer looking at.

The files table on a run page works the same way, with the same bar at the bottom of the window. Its rows have no buttons of their own either. Select the checkboxes of the files you want to act on, and the bar offers **Upload**, **Download**, **Reprocess**, and **Dismiss** for only those files. Its **Upload** follows the instrument’s badge, like the other [Upload buttons](#request-upload). The selection stays when you move to another page of the table, and it clears when you change the files search, a filter, or the sort.

The files table of a deleted run has no checkboxes, so nothing in it can be uploaded, reprocessed, or dismissed until you restore the run. Its rows still open the file window.

![Run list with several runs selected and the bulk action bar open](/images/bulk-actions.webp)

## Comment on a run [#comment]

The comment thread on a run page is for lab notes and follow-ups. A new comment can notify the people who claimed the run or already commented on it, and choosing a comment notification scrolls to that comment. Set preferences under **Settings → Notifications**; see [Configure notifications](/docs/configure-notifications).

Only the author of a comment can edit it. Authors can delete their own comments, and admins can delete any comment. Comments posted by a script through an API token show the token’s name with a key icon instead of a person.

![Gel doc processed image with a lab comment on the run](/images/gel-doc-run-comments.webp)

## Reprocess or delete a run [#reprocess-and-delete]

Reprocessing runs server-side processing again. Use it after a file failed or stalled, or after an engineer fixes the code that reads a file type. The stored result doesn’t change until you reprocess.

- On the run page, select one or more files in the files table and choose **Reprocess** in the bar at the bottom of the window.
- To reprocess whole runs, select them in a run list and choose **Reprocess** in the bar.

Reprocessing sends only the original instrument files. Files Data Hub generated, such as videos, previews, and CSVs, can’t be reprocessed themselves and are rebuilt from the originals. Reprocessed files go through a queue; see [How reprocessing is queued](#reprocess-queue).

**Delete** marks the run deleted without removing its stored files. Anyone signed in can delete or restore a run. To find a deleted run, turn on **Show deleted runs** under **Add filter**, then open it and choose **Restore**.

Files that were queued for reprocessing when the run was deleted stay queued but don’t start. If you restore the run, they start as processing slots free up.

Deleting a run also cancels the uploads that were requested for its files, so the watcher stops trying to send them, and those files go back to **Not uploaded**. Restoring the run doesn’t bring the requests back, so choose **Upload** again if you still want the files; see [Request an upload](#request-upload).

While a run is deleted, Data Hub refuses a watcher’s reports of it, so the watcher’s new files aren’t added. After you restore the run, restart the watcher to send them, or select the file and choose **Upload** to have the watcher send that file without a restart. Watchers before 1.4.3 also send them when another file of the run finishes. See [A run was deleted on Data Hub](/docs/troubleshoot-a-watcher#a-run-was-deleted-on-data-hub).

![Deleted run page with a red banner naming who deleted it and when, and a Restore button](/images/deleted-run.webp)

### How reprocessing is queued [#reprocess-queue]

Reprocessing starts at most 10 files at a time, counted across all runs and instruments. When you choose **Reprocess**, each file goes into a queue:

- A file that can start right away shows **Processing**.
- A file that has to wait shows **Queued**. It starts when another file finishes, and files that were queued earlier start first.
- A run with queued files shows **Queued** in the runs list, unless another of its files has a status that comes earlier in the [status table](#run-status), such as **Failed**.
- If Data Hub can’t send a file to the processor, or the processor ends with an error without saving a result, the file shows **Failed** with a message that says so, and the next queued file starts. Reprocess the failed file to try again.
- To take the waiting files out of the queue, choose **Cancel queued** at the top of the run page. Each queued file shows **Failed** with a message that says the reprocess was cancelled, and you can reprocess it again. Files that have already started aren’t affected.

Files that arrive from a watcher upload count toward the 10, but they start right away and never wait in the queue. A file that has been processing for more than 20 minutes without finishing stops counting, so one stuck file doesn’t hold up the queue.

A large run takes several rounds. For example, reprocessing a run of 80 files starts 10 files, and the other 70 show **Queued** until slots open. You can leave the page, because the queue keeps running. A queued file can’t be reprocessed.

The engineer who deploys Data Hub can change the limit of 10 with the `PROCESSING_CONCURRENCY_LIMIT` environment variable; see the [web application environment variables](https://github.com/Arcadia-Science/data-hub/blob/production/docs/developer/getting-started.md#web-application).

If a file that the queue started never finishes, for example because Data Hub restarted at the moment it started the file, it shows **Stalled** after 20 minutes. The queue then puts it back in line once. If it stalls a second time, it stays **Stalled** until you reprocess it.

## Get files that are still on the instrument PC [#files-on-the-pc]

The watcher reports every file it finds, but some files stay on the instrument PC until someone asks for them, and some fail to upload. The footer under a run’s files table counts the files still on the instrument PC, the files that couldn’t upload, and the files uploaded.

### Request an upload [#request-upload]

A file that the watcher found but nobody requested reads **Not uploaded**. To ask the watcher to send files, do one of these:

- Select one or more files and choose **Upload** in the bar at the bottom of the window
- Choose **Upload all** at the top of the **Files** section, for every file in the run that reads **Not uploaded** or **Upload failed**

A requested file reads **Uploading** until it arrives. The watcher picks up requests within a minute.

On an instrument that uploads automatically, a new file reads **Waiting to upload** until the watcher sends it. This needs watcher 1.4.5 or later; with an older watcher the file reads **Not uploaded** for the minute or two before it arrives.

The **Upload** action in the files bar and the **Upload all** button on a run page follow the instrument’s badge. When one is turned off, the reason shows beside it:

| Badge | Upload buttons | Beside them |
| --- | --- | --- |
| **Online** | On | Nothing |
| **Restarting** | On. Requests wait until the watcher is back | “The instrument PC is restarting. Uploads start once it’s back.” |
| **Connecting** | Off | “The watcher hasn’t checked in yet.” |
| **Offline** | Off | “Can’t upload while the watcher is offline.” |
| **Pending** | Off | “This instrument is waiting for an admin to confirm it.” |
| **Retired** | Off | “This instrument is retired.” |

If the badge reads **Offline** and the run has files that are still on the instrument PC, a red notice sits above the **Files** section. It says how many files are still on the PC, which watcher isn’t running, and when it last checked in, and links to **See details**. A run with no waiting files never shows the notice, whatever the badge says.

![Run page for an offline instrument, with a notice that four files are still on the instrument PC and a turned-off Upload all button with the reason beside it](/images/run-offline-notice.webp)

A request made while the instrument reads **Restarting** waits, and the watcher uploads the files once it’s back. If the watcher doesn’t check in for about 15 minutes, Data Hub cancels the request and the files read **Not uploaded** again. [Request uploads](/docs/manage-watchers#request-uploads) lists every case that cancels a request.

The **Upload** button on a runs list doesn’t follow the badge. Select runs and choose it to ask for every waiting file in them. For an instrument that is **Offline**, **Connecting**, **Pending**, or **Retired**, Data Hub refuses that run’s request, and a message reports how many runs failed. Choose **Upload** from the run page instead to see why.

On an instrument in [manual upload mode](/docs/concepts#upload-mode), every file waits until someone chooses **Upload** for it. **Dismiss** tells the watcher not to upload a file. See [Manage the watcher fleet](/docs/manage-watchers#approving-manual-uploads).

![Run page for a manual-upload instrument with its waiting files selected and a bar offering Upload and Dismiss](/images/manual-upload.webp)

### When an upload fails [#upload-failed]

The watcher gives up on a file when it can’t send it. The file then reads **Upload failed**, and hovering over the status shows why:

- **The folder is no longer on the instrument PC.** Someone renamed or moved the run’s folder after the watcher found it. The watcher reports the folder under its new name as a new run, so look for a run with the same start time and a similar name.
- **The file isn’t on the instrument PC.** The folder is there but the file was moved or deleted.
- **The upload kept failing.** The watcher tried and the upload failed each time, for example because of a network problem. The message shows the last error.
- **The path is outside the watch folder.** The watcher won’t upload a file outside the folder it watches.

For a requested file, the watcher checks three times, about a minute apart, before it gives up. On an instrument that uploads automatically, it gives up as soon as an upload fails, and it tries again the next time it starts.

A red notice above the **Files** section lists the files that couldn’t upload, one block per reason and folder. Each block says why and when the watcher gave up. The run reads **Upload failed** until every such file is uploaded or dismissed, and the watcher’s activity shows one **Couldn’t upload** entry per run and reason.

Once the cause is fixed on the PC, choose **Upload again** in the block, or select a file and choose **Upload**, to try again. If the files are gone for good, choose **Dismiss these files**.

Whoever requested the files gets one notification per run and reason, in the app and, if they connected Slack, as a direct message. See [Configure notifications](/docs/configure-notifications).

Marking files **Upload failed** needs watcher 1.4.5 or later. An older watcher puts the file back to **Not uploaded** instead, without a reason; see [Roll out watcher releases](/docs/watcher-releases#what-each-version-adds).

## Use the same data outside the UI [#programmatic-access]

You can also list and fetch the same runs and files over the [REST API](/docs/api) or the [Model Context Protocol (MCP) endpoint](/docs/mcp). REST needs a [personal access token](/docs/concepts#personal-access-token); scopes and creation are covered in [Issue and revoke tokens](/docs/manage-tokens). MCP clients sign in through the browser instead, and clients that support MCP Apps show the same interactive run report you see here.
