<Audience>Lab operators, admins, and engineers</Audience>

After a [watcher](/docs/concepts#watcher) uploads a raw file, Data Hub can run a **processor** on it. A processor is code that reads the vendor’s file, pulls out settings like wavelength or imaging mode, and builds something you can look at in the browser. Nine instrument types have one today. This page covers what each processor produces, why a file sometimes gets no processing, and what adding a new instrument involves.

<Callout type="warn">
  Supporting a new instrument is engineering work that an admin can’t do in settings. It needs a new Python module, a database migration, changes to both the web app and the Lambda (the AWS function that processes files), and a Lambda redeploy. See [Add support for a new instrument](#add-support-for-a-new-instrument).
</Callout>

## How a file reaches a processor [#how-preprocessing-works]

1. A file arrives in raw storage, which starts the Lambda. Storage starts it for every upload, whatever the instrument.
2. The Lambda checks whether any processor accepts the file’s type. If none does, it stops there, before it contacts the Data Hub API.
3. It looks up the instrument, then finds the processor for the instrument’s [type](#set-the-instrument-type). It stops here when the type has no processor, or when that processor doesn’t accept the file’s type.
4. The processor reads the file, extracts metadata, writes processed files when it has any, and updates the run through the API.
5. The file’s status moves from `processing` to `completed` or `failed`.

### Why an upload sometimes produces nothing [#why-an-upload-produces-nothing]

Two things can make an upload produce nothing, and neither marks the file failed, because nothing went wrong:

- **The processor doesn’t accept the file’s type**: each processor accepts only the file types listed in the table below. A TapeStation run starts processing only on its PDFs, so the peak-table CSVs it writes are stored but don’t start processing on their own.
- **The instrument has no type set, or a type with no processor**: files upload and stay browsable, but you get no metadata and no reports.

The file-type check also applies when you choose **Reprocess** in the web app. Reprocessing a file that the processor doesn’t accept marks it **Failed**, with a message that names the instrument type. Reprocessing does help when the instrument had no type, or a type with no processor, when the file arrived: set the type, then choose **Reprocess**.

### Set the instrument type [#set-the-instrument-type]

Data Hub picks the processor by the instrument’s **type**, not its instrument ID. The ID (`azure-cielo-qpcr`) names one physical machine. The type (`qpcr`) names a vendor’s file format, and several instruments can share one.

To set it, open the instrument page as an admin, choose **Edit details** from the three-dot menu, and choose an **Instrument type**.

![Edit instrument window with the display name and instrument type fields](/images/instrument-edit-dialog.webp)

<Callout type="warn">
  One type means one vendor’s output format. Names like `qpcr` and `fplc` sound general, but each belongs to a single vendor’s processor: `fplc` expects ÄKTA PDFs, and `qpcr` expects Azure Cielo exports. Giving a different vendor’s instrument an existing type sends its files to a processor that can’t read them. Supporting a second vendor means splitting the type in two, which is a code change.
</Callout>

## Supported instrument types [#supported-instruments-at-a-glance]

| Type | Vendor and model | File types it processes on upload | You get |
| --- | --- | --- | --- |
| `tape_station` | Agilent 4150 TapeStation | `.pdf` | Tape-type badge, PDF reports |
| `fplc` | Cytiva ÄKTA FPLC | `.pdf` | PDF you can read on the run page, no metadata |
| `gel_doc` | Azure 600 Gel Doc | `.tif`, `.tiff` | Contrast-enhanced PNG, imaging badges |
| `qpcr` | Azure Cielo qPCR | `.csv`, `.pdf`, `.aze` | Dye-channel badges, melting curves, the instrument’s PDF report |
| `epson_v700_scanner` | Epson V700 Scanner | `.tif`, `.tiff` | Plate preview JPG, colony measurements |
| `hina_microscope` | Hina Microscope (Nikon ND2) | `.nd2` | Channel overlay JPG, a video of each timelapse, channel badges |
| `plate_reader` | SpectraMax iD3 and iD5 | `.xls` | Well-data CSV, interactive plate maps |
| `dishcam` | DishCam time-lapse camera | `.tif`, `.tiff`, `run.json` | A video of each photo stack, camera-setting badges |
| `aunty` | Unchained Labs Aunty | `.xlsx` | A plate with a curve chart in each well, experiment badges |

## Agilent 4150 TapeStation [#agilent-4150-tapestation]

Reads the tape type out of peak-table CSV filenames and shows TapeStation reports on the run page.

- **Expected files**: CSVs named like `YYYY-MM-DD - HH-MM-SS-<TapeType>_peakTable.csv`, plus matching PDFs
- **Metadata**: `Tape Type`, for example `gDNA` or `HSD1000`, when the filename matches that pattern
- **Processed files**: none
- **On the run page**: tape-type badge, a PDF viewer, and peak-table reports

Only the PDF starts processing. A run with only CSVs stays unprocessed, and choosing **Reprocess** on one of its CSVs marks it **Failed**, because the TapeStation processor accepts only PDFs.

## Cytiva ÄKTA FPLC [#akta-fplc]

Stores ÄKTA chromatography PDFs so you can read them in the browser. The processor reads nothing out of the PDF itself yet, so this type gets no badges or filters.

- **Expected files**: `.pdf` reports from the ÄKTA
- **Metadata**: none
- **Processed files**: none
- **On the run page**: files table, plus each PDF embedded under **Report Data**

Leave a new FPLC as `generic` until an operator has checked that its PDFs are ÄKTA reports.

## Azure 600 Gel Doc [#azure-600-gel-doc]

Rebuilds each gel TIFF as a viewable image and reads the imaging settings the instrument recorded.

The processor stretches the contrast of each image, so the darkest 1% of pixels show as black and the brightest 1% show at full brightness. It does this per RGB channel, or once for a grayscale image. Then it lays every page of the TIFF side by side in one 300 dpi PNG. The stretch makes faint bands visible on screen and doesn’t change the raw file.

- **Expected files**: TIFF from the Azure 600
- **Metadata**: `capture_type`, `imaging_mode` (true color, fluorescence, or chemiluminescence), `wavelengths`, `colors`, read from the TIFF `XPComment` tag
- **Processed files**: contrast-enhanced PNG
- **On the run page**: imaging badges, files table, image viewer for the PNGs

Those metadata fields also drive the column filters on the instrument page.

## Azure Cielo qPCR [#azure-cielo-qpcr]

Reads dye channel names, melting curves, and the instrument’s PDF report.

- **Expected files**:
  - the Cq Values CSV, for dye channels
  - the melting curve CSV (a name ending in `_MeltingCurve.csv`)
  - the PDF report the instrument writes
  - `.AZE` project files
- **Metadata**: `dye_channels`, the unique names in the Cq Values CSV’s `Fluorescence` column
- **Processed files**: `{run_id}_melting_curve_derivatives.csv` and `{run_id}_melting_curve_plate.json` from the melting curve CSV. An `.AZE` file produces `{run_id}_aze_melting_curve_derivatives.csv`, `{run_id}_aze_melting_curve_plate.json`, and `{run_id}_aze_experiment.json`.
- **On the run page**: dye-channel badges, the PDF report under **Report Data**, and a **Melting Curves** section

The **Melting Curves** section shows the plate for one dye channel at a time. Select a well to see its melting curve and derivative, with a dashed line at the melting temperature. A run with more than one PDF gets previous and next buttons under **Report Data**.

![qPCR run page with dye-channel badges, the files table, and a Melting Curves plate showing a derivative curve in each well](/images/qpcr-run-detail.webp)

The other CSV files a qPCR run writes upload normally and show as completed, but contribute no metadata.

### `.AZE` project files [#aze-project-files]

Data Hub reads melting curves from the Azure Cielo’s native `.AZE` project files as well as from the CSV export. Melting temperatures match the CSV export, but other values can differ. That’s because `.AZE` files store raw fluorescence, while the CSV export can be adjusted for baseline. A project with no melt data completes with no processed files.

The watcher uploads `.AZE` files only when `*.AZE` is in the instrument’s file patterns. Patterns are case-sensitive, so match the case the instrument uses. See [Watcher configuration](/docs/configuration-reference#field-reference).

An admin can add the pattern on the **Settings** tab of the instrument’s watcher page; see [Change a watcher’s settings](/docs/manage-watchers#change-a-watchers-config). You can also add it on the instrument PC with `data-hub-watcher config edit` and restart the watcher.

## Epson V700 Scanner [#epson-v700-scanner]

Finds agar plates in a flatbed scan and measures the colonies on them.

The processor looks for plates sitting in gold 3D-printed frames. For each plate it finds, it crops the plate and then detects colonies:

1. Trims the edge of the plate
2. Compares the plate against its background
3. Applies a difference-of-Gaussians filter, a standard way to pick out small spots
4. Applies a threshold
5. Measures whatever is left

Measurements come out in physical units, so colony areas are comparable between scans.

- **Expected files**: TIFF plate scans
- **Metadata**: `dpi`, `color_mode`, `plate_count`, `plate_boxes`, plus `colony_detection` summaries when colonies were measured
- **Processed files**: a web-sized JPG with plate outlines and colony boxes drawn on, and a `_colonies.csv` of per-colony area, centroid, eccentricity, and mean RGB
- **On the run page**: scanner badges, files table, and reports for the processed CSV

When no plates are found, you still get a resized JPG of the whole scan, and colony detection is skipped. An empty `plate_count` most likely means the frames weren’t recognized, not that the plates were blank.

## Hina Microscope [#hina-microscope]

Turns each Nikon ND2 into a composite image you can view in the browser, and each timelapse into a video.

For each time point, the processor turns every channel into one 2D frame. It takes the maximum projection over Z (the brightest value through the stack) and the first index over position. It reads one frame at a time, so large stacks process without loading the whole file.

The processor stretches each frame’s contrast so the darkest 1% of pixels show as black and the brightest 1% at full brightness. Then it lays the channels over a brightfield background, each in its fluorophore color.

- **Expected files**: ND2
- **Metadata**: `sizes`, `channels` (name, excitation and emission wavelength, color), and `dimensions`. Each timelapse file also records `frames`, `frame_interval_ms` (the measured time between frames), and `playback_fps` in its own file metadata.
- **Processed files**: an RGB overlay JPG of the first time point for every file in the run, plus an MP4 for every file with more than one time point
- **On the run page**: channel and size badges, files table, and a viewer with one item per file. A timelapse plays as a video, with its JPG shown before you press play. Any other file shows its JPG.

A timelapse video plays at the capture rate or at 10 frames per second, whichever is faster, so slow captures stay watchable. A file that doesn’t record the time between frames plays at 10 frames per second.

Each channel’s contrast comes from the first frame and stays the same for the whole video, so brightness doesn’t flicker and the first frame matches the JPG. Pixels that later grow brighter than the brightest 1% of the first frame show at full brightness. A signal that grows strongly during the capture can therefore look saturated.

If the video can’t be made, the file shows **Failed** and the message says why. One cause is a timelapse that can’t finish within the [15-minute processing limit](#when-processing-fails). The JPG and the raw file are still available.

A timelapse processed before Data Hub made videos gets its video when you reprocess the file or its run; see [Reprocess or delete a run](/docs/browse-runs#reprocess-and-delete). Timelapses take several minutes each. When you reprocess a run with more than 10 of them, 10 process at a time and the rest show **Queued**.

Every file in a Hina run has the same channel layout, so whichever file finishes processing first writes the run’s metadata. Later files still get their JPG but skip the metadata write. If the layout changed partway through a run, reprocessing one file won’t correct the run’s metadata.

An image too large to preview at full size gets a smaller preview instead. For example, a 6221 × 6221 pixel image is previewed at 3110 × 3110 pixels. The raw file is unchanged, and you can download it at full size. A file that showed **Failed** for this reason earlier gets its preview when you reprocess the file or its run.

Two kinds of image still show **Failed** instead of a preview:

- An image from a color camera, which Data Hub can’t preview yet
- An image far larger than the Hina Microscope has produced so far

The message on the file says which. In both cases the raw file is stored and you can download it.

## SpectraMax iD3 and iD5 plate readers [#spectramax-id3-and-id5-plate-readers]

Both models share one processor, which converts SoftMax Pro exports into the well data behind the interactive plate maps.

- **Expected files**: SoftMax `.xls`, which is UTF-16 text with a `Plate:` header rather than a real Excel workbook
- **Metadata**: `measurement_mode` (Absorbance, Fluorescence, or Luminescence), `measurement_type` (Endpoint, Kinetic, Spectrum, or Well Scan), and `wavelengths` as bare numbers with no unit suffix
- **Processed files**: `{run_id}_raw_well_data.csv`
- **On the run page**: wavelength, mode, and type badges, plus plate maps built from that CSV

What the plate map shows depends on the read:

- **Kinetic** reads get a time slider. Reads that skip the edge wells keep their time values, and runs that SoftMax Pro stopped early still process.
- **Spectrum** reads (wavelength scans) get a wavelength slider.
- **Luminescence** reads show no wavelength, because luminescence doesn’t use one.

SoftMax Pro writes `#SAT` in a saturated well and `#Low` when the flash lamp missed a well. Those wells show as blank on the plate map, and the rest of the file processes normally.

## DishCam [#dishcam]

Turns each DishCam photo stack into a video you can play on the run page.

- **Expected files**: multi-page TIFF photo stacks, plus the `run.json` file the camera writes next to them
- **Metadata**: camera settings from `run.json`: `fps`, `measured_fps`, `frames`, `duration_seconds`, `quality`, `format`, `started`, and `finished`
- **Processed files**: an MP4 video and a JPEG still frame for each stack
- **On the run page**: a video player at the top of the report, with play, pause, and a timeline you can drag. The still frame shows before you press play.

The video plays at the capture rate or at 10 photos per second, whichever is faster, so slow captures stay watchable. The stored `fps` metadata still records the real capture rate.

A stack processes once both the stack and its `run.json` are in storage, in either order. When a run gathers captures from several folders, each stack uses the `run.json` from its own folder. When two folders both have a `run.json`, the watcher renames later copies with a short tag, such as `run~3f9a1c2b.json`.

Large stacks are read one photo at a time. If a stack can’t finish within the [15-minute processing limit](#when-processing-fails), it shows **Failed**, and the message says how far through the photos it got. You can still download the raw file.

## Unchained Labs Aunty [#unchained-labs-aunty]

Reads Aunty exports, which measure protein melting temperature and particle size, and draws a plate of curves.

- **Expected files**: the `.xlsx` export from the Aunty software. Thermal ramps, sizing runs, isothermal holds, and exports that contain only the results table without curves all process.
- **Metadata**: `experiment_type` (`thermal_ramp`, `sizing`, or `isothermal`), `experiment_count`, and the first experiment’s settings: `analysis_mode`, `start_temp_c`, `end_temp_c`, `rate_c_per_min`, `temperature_c`, `analysis_version`, and `experiment_name`
- **Processed files**: `{run_id}_aunty_curves.csv`, with every curve point for every well, and `{run_id}_aunty_plate.json`, which drives the plate view
- **On the run page**: a plate with a small chart in each well. Select a well to open its full chart.

![Aunty run page with the experiment type and temperature badges, the files table, and a plate with a small curve in each well](/images/aunty-run-detail.webp)

On the instrument page, filter Aunty runs by experiment type, analysis mode, temperature, and ramp rate.

## Types with no processor [#instruments-without-a-matching-processor]

Instruments typed `generic` or `instant_raman`, and instruments with no type set, upload without processing. Their files are stored, and you can browse, search, claim, comment on, and download them. They get no extracted metadata, badges, filters, or processed files.

Leave a new instrument as `generic` until someone confirms which processor, if any, can read its files. Its files keep uploading in the meantime.

## When processing fails [#when-processing-fails]

A file with status `failed` shows an error message on the run page. Open the run, select that file, and choose **Reprocess**, or select runs in a run list and choose **Reprocess**. See [Reprocess or delete a run](/docs/browse-runs#reprocess-and-delete).

Processing one file has a 15-minute limit. A file that hits the limit, or is too large to process at all, shows **Failed** with a message that explains why. The raw file stays in storage, and you can download it.

A file that stays in processing for more than 20 minutes without finishing shows **Stalled**. That most likely means the processor stopped without reporting back. Reprocess it to try again.

Reprocessing puts a file in a queue and starts at most 10 files at a time. A file that has to wait shows **Queued** until a slot opens. See [How reprocessing is queued](/docs/browse-runs#reprocess-queue).

Reprocess files after an engineer fixes a processor, too. The fix changes the code, but results already stored stay the same until you reprocess.

## Add support for a new instrument [#add-support-for-a-new-instrument]

<Audience>Engineers</Audience>

Adding an instrument type is development work in the web app and the Lambda. Plan for a database migration and a Lambda image deploy.

<Steps>

<Step>
**Add the type.** Extend `instrumentTypeEnum` in `web/lib/db/schema.ts` and generate an `ALTER TYPE … ADD VALUE` migration. Reuse an existing type only when the new instrument writes the same vendor’s format.
</Step>

<Step>
**Write the processor.** Add a module under `lambda/src/data_hub_lambda/` with a `process_file(instrument_id, run_id, filename)` function that reports progress through the Data Hub API.
</Step>

<Step>
**Register it twice.** Add the type to `PROCESSORS` in `lambda/src/data_hub_lambda/processors.py`, with the file types it accepts, and to `PROCESSABLE_INSTRUMENT_TYPES` in `web/lib/instruments/processable-types.ts`. These two lists have to agree. The Lambda uses the first to pick a processor, and the web app uses the second to decide whether to offer **Reprocess**.
</Step>

<Step>
**Add tests** for the processor and for the file types it accepts.
</Step>

<Step>
**Deploy the Lambda image.** The raw bucket already starts the Lambda for every upload, so you don’t need a new S3 trigger.
</Step>

</Steps>

To try a processor on your own machine without S3 or API access, use the `data-hub-process` CLI. Its `handler` subcommand runs the whole handler against a local copy of S3.

Full detail, including the archive builder and the Docker build, is in [the Lambda developer docs](https://github.com/Arcadia-Science/data-hub/blob/production/docs/developer/lambda.md#adding-a-new-instrument--processor).
