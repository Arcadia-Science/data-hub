<Audience>Lab operators and admins</Audience>

Find your symptom below. When you are stuck, the [logs](#where-are-the-logs) are the fastest way in. Admins can also inspect events, heartbeats, and settings on the instrument’s watcher page: select the status badge beside the instrument’s name, or choose **Watcher** from its three-dot menu. Members can open that page too, to read it.

## An instrument shows Offline [#instrument-shows-offline]

An instrument’s badge reads **Offline** when new files can’t reach Data Hub right now. A notice under the instrument’s name says why, and **See details** opens the watcher’s **Activity** tab. Find the notice below.

| Notice | What it means | What to do |
| --- | --- | --- |
| **New files aren’t being picked up** | The watcher is running but can’t find its watch folder. | Create or reconnect the folder on the PC, or let an admin choose **Change folder**. See [The watcher shows “Waiting: folder not found”](#waiting-folder-not-found). |
| **The watcher isn’t checking in** | No heartbeat for 5 minutes, or the watcher didn’t come back within 15 minutes of a restart or an update. The PC may be off, the watcher may have crashed, or the network may be blocking Data Hub. | On the PC, check that the watcher is running (`data-hub-watcher service status` on Windows) and that it can reach Data Hub; see [“Connection error” or “Request timed out”](#connection-error-or-request-timed-out). Its last events are on the **Activity** tab. |
| **Uploads from this instrument are paused** | Someone stopped the watcher, for example with `data-hub-watcher service stop` or Ctrl+C. | Start it again: `data-hub-watcher service start` on Windows, or `data-hub-watcher watch`. |
| **This instrument isn’t connected to a watcher** | The instrument never had a watcher, or its watcher was deregistered, which the notice dates and credits. | Run `data-hub-watcher init` on the PC; see [The watcher stopped and says it was deregistered](#the-watcher-was-deregistered). Admins can follow **Connect a watcher**. |

**Restarting** and **Connecting** aren’t problems. See [The instrument shows Restarting after a restart](#the-instrument-shows-restarting-after-a-restart). Files saved on the PC while an instrument is offline stay there, and the watcher picks them up once it runs again.

## Setup and registration

### “Instrument is still pending activation”

The instrument was registered but an admin has not confirmed it. Its badge reads **Pending**. Ask an admin to open **Instruments**, click **Confirm…**, pick an instrument type, and choose **Confirm instrument**. See [Manage instruments](/docs/manage-instruments#confirm-a-pending-instrument).

### “Instrument already has an active watcher”

Each instrument can have at most one active watcher. An earlier install (often on another PC, or before a reimage) is still registered. The CLI prints the existing watcher id; deregister it before re-running `init`:

- **Web app**: open the instrument, select its status badge to open its watcher page, and choose **Deregister** from the ⋮ menu. You can also use the row menu in **Settings → Watchers**. Only admins see those menus. Watcher 1.4.3’s message names a menu that no longer exists; watcher 1.4.4 prints the address of the watcher’s page instead
- **API**: `DELETE /api/v1/watchers/<existing_watcher_id>` with a bearer token that has `watchers:admin`

Deregistration is a soft-delete: the history stays with the instrument as a past watcher, and on the **Deregistered** tab of **Settings → Watchers**.

### `init` rejects my API key

The wizard rejects values that do not start with `dhub_`, and strips zero-width and non-breaking-space characters that Windows clipboards inject. If a paste keeps failing, pass `--show-key` so you can see what the prompt received.

## The watcher will not start

- Run `data-hub-watcher config show` to confirm config and environment
- Run `data-hub-watcher watch --dry-run`: it prints the first failing check
- Confirm the instrument is `active`, not `pending`
- On Windows, if the **service** will not start, see [Windows service](#windows-service)

## The watcher stopped and says it was deregistered [#the-watcher-was-deregistered]

Someone deleted the watcher’s registration on Data Hub. This happens when an admin deregisters the watcher in the web app, or retires its instrument (see [Deregister a watcher](/docs/manage-watchers#deregister-a-watcher)). After a deregistration, the instrument reads **Offline** and its notice says its watcher was deregistered. A retired instrument reads **Retired**, with no notice. Watcher 1.4.3 and later stop by themselves when this happens. The watcher logs one error:

`This watcher was deregistered on Data Hub, so its registration no longer exists. Run 'data-hub-watcher init' to register it again.`

You can find that error in `watcher.log` (see [Where are the logs?](#where-are-the-logs)). On Windows, it is also in the Application event log, and `service status` shows the service as stopped.

The watcher waits for three heartbeats in a row that Data Hub answers with its “deregistered” reply. At the usual one-minute interval, that is about three minutes, so one wrong answer can’t stop the watcher. A different error, including Data Hub saying it has no watcher with that ID, doesn’t stop it. Once it has stopped, it uploads nothing and doesn’t come back on its own. Starting it again is refused with the same message. `watch` exits with code 3 when it stops this way, and when it refuses to start.

To use the PC again, run `data-hub-watcher init` on the PC. This registers a new watcher for the instrument. If the instrument was retired, `init` is refused until an admin reactivates the instrument (see [Reactivate](/docs/retire-an-instrument#reactivate)). The PC keeps its upload history, so files that were already uploaded aren’t uploaded again. If `init` reports that the instrument already has an active watcher, see [Instrument already has an active watcher](#instrument-already-has-an-active-watcher). On Windows, then run `data-hub-watcher service start` from an Administrator terminal.

Watchers older than 1.4.3 don’t stop. They keep running and get errors from Data Hub until someone stops them.

## The watcher shows “Waiting: folder not found” [#waiting-folder-not-found]

Watcher 1.4.0 and later start even when the watch folder is missing, for example when a network drive isn’t connected yet or the folder was renamed. The watcher keeps sending heartbeats but watches nothing. Its page shows **Waiting: folder not found**, and the instrument reads **Offline** with the notice “New files aren’t being picked up”. Hover over the watcher’s badge to see which folder it’s looking for; the notice names it too.

The watcher checks for the folder again once a minute and starts watching as soon as it appears. To fix it:

- Create or reconnect the folder on the PC, or
- Point the watcher at the right folder from the web app: an admin chooses **Change folder** in the notice, which opens the watcher’s **Settings** tab with the **Watch folder** field selected; see [Change a watcher’s settings](/docs/manage-watchers#change-a-watchers-config)

Watcher 1.4.3 and later also go back to this state when the folder disappears while they run, for example when a network drive drops or the folder is deleted. The watcher notices within a minute, looks again a few seconds later so that a drop of a moment doesn’t count, stops watching, and shows **Waiting: folder not found**. It gives a file that was uploading at that moment up to 10 seconds to finish, cuts it off if it isn’t done, and uploads it again once the folder is back. When the folder returns, the watcher starts watching it again without a restart, and queues a `watcher_started` event that says it resumed.

Older watchers exit at startup instead, with an error that the watch directory doesn’t exist.

## A config change shows “Change rejected” [#change-rejected]

The watcher checked a change made in the web app and refused it, so it kept its previous settings. The reason shows in a **Change rejected** notice on the watcher’s **Settings** tab and as an `error` event with `details.kind` set to `config_revision_rejected`. The most common reason is a folder that doesn’t exist or can’t be read on the PC. Fix the cause, then save the change again or **Restore** an earlier version from the history.

## “Data Hub can’t read the watcher’s config file” [#config-file-unreadable]

The watcher’s **Settings** tab shows this when the `config.yaml` the watcher sent breaks the rules the web app checks, for example a relative watch folder, more than 50 file patterns, or a run detection pattern with Python-only syntax such as `(?P<name>…)`. The notice names each field that needs fixing, by its key in the file.

Until it’s fixed, edits made on the PC aren’t recorded in the history, and if Data Hub has no earlier revision of the settings, there are none to edit there. Fix the file on the instrument PC, for example with `data-hub-watcher config edit`.

## A config change stays on “Change pending” [#change-pending]

The watcher picks up a change after its next heartbeat, within about a minute. If it stays pending:

- Check that the watcher is **Online** on its page. An offline watcher applies the change when it next starts.
- Check that the watcher runs 1.4.0 or later. The web app won’t save changes for older watchers.

## The instrument shows Restarting after a restart [#the-instrument-shows-restarting-after-a-restart]

When the PC restarts, or the watcher stops to install an automatic update, the instrument’s badge reads **Restarting** for up to 15 minutes, not **Offline**. Nothing is wrong. The watcher checks in once a minute, so it can take up to a minute after the service starts to show as **Online**. Refresh the page after a minute. A new watcher reads **Connecting** until its first check-in.

If the badge turns **Offline** with the notice “The watcher isn’t checking in”, the watcher didn’t come back. Check that the process is running and see [“Connection error” or “Request timed out”](#connection-error-or-request-timed-out). Older watchers don’t say they are restarting, so they read **Offline** from the moment the PC goes down; see [When the PC restarts or shuts down](/docs/windows-service#when-the-pc-restarts-or-shuts-down).

## Heartbeats fail with `426 Upgrade Required`

The watcher is older than the **Minimum supported version** an admin set under **Settings → Watchers**, so the server rejects its heartbeats and it shows as unresponsive. Its instrument reads **Offline**. It keeps checking for updates every hour and upgrades itself if **Latest version** is newer. To upgrade now, run `data-hub-watcher self-update`. See [Roll out watcher releases](/docs/watcher-releases#release-config-fields).

## “Connection error” or “Request timed out” [#connection-error-or-request-timed-out]

The watcher cannot reach the Data Hub API. Check:

- Network connectivity from the instrument PC
- Environment in config (`staging`, `production`, or `preview`): `data-hub-watcher config show`
- That the API base URL for that environment is reachable

### A run is missing after a connection problem [#a-run-is-missing-after-a-connection-problem]

Watcher 1.2.2 and later retry a run report that failed because the watcher couldn’t reach Data Hub, or because Data Hub returned a server error. The first retry comes after 5 seconds. The wait then doubles up to 5 minutes between tries, and the watcher keeps trying every 5 minutes until the report goes through. It needs no new file and no restart, so the run appears on its own once the problem clears.

The watcher records one `run_report_failed` event when a run’s report first fails. It doesn’t record another for the same run while it keeps retrying, even if more files in the run finish in the meantime.

A failure that isn’t a connection problem or a server error, such as `401 Unauthorized`, is not retried, because it would fail the same way. Each one is recorded, except the refusals of a run that was deleted on Data Hub, which watcher 1.4.3 and later record once per run (see [A run was deleted on Data Hub](#a-run-was-deleted-on-data-hub)). Fix the cause, then restart the watcher.

Older watchers try again only when another file in the run finishes or the watcher restarts. Restart the watcher to report the run.

## A run was deleted on Data Hub [#a-run-was-deleted-on-data-hub]

A run report or an upload request that fails with `409 Conflict` and a message that starts “This run was deleted on Data Hub” means someone deleted the run. Data Hub refuses a watcher’s report of a deleted run, and its requests to upload the run’s files, and the files in a refused report aren’t added to the run.

Watcher 1.4.3 and later record one event for the run, a `run_report_failed` event or an `upload_failed` event, whichever the watcher meets first, and stop reporting the run and uploading its files until the watcher restarts. A restart tries once more, and records one more event if the run is still deleted. After you restore the run, restart the watcher to send its files. A file that someone requests with **Upload** on the run page doesn’t wait for the restart: the watcher asks Data Hub for each requested file, and once Data Hub accepts one, the watcher reports and uploads the run’s new files again.

Earlier watchers record one event for each file, and do it again each time they start. After you restore the run, they send its files when another file of the run finishes or the watcher restarts.

To stop the errors without restoring the run, move the run’s files out of the watch folder.

## Files are not being detected

- Confirm the watch directory and file patterns. The instrument’s page in the web app shows both, or run `data-hub-watcher config show` on the PC. Admins can change them from the web app; see [Change a watcher’s config](/docs/manage-watchers#change-a-watchers-config)
- Check that the instrument saves its files into that folder, not a shared network drive or another folder
- Check file patterns. Globs are case-sensitive (`*.csv` does not match `data.CSV`)
- If files live in subfolders, set run detection to recursive; see [Configure run detection and uploads](/docs/configure-run-detection)
- Run `data-hub-watcher watch --dry-run` to preview matches
- Look for `pattern_mismatch` events on the watcher’s **Activity** tab

## Files are detected but not uploading

- In **manual** mode, files wait for approval in the upload queue; see [Manage the watcher fleet](/docs/manage-watchers#approving-manual-uploads)
- On the run page, the **Upload** buttons are turned off while the instrument is **Connecting**, **Offline**, **Pending**, or **Retired**, with the reason beside them. Fix the watcher first; see [An instrument shows Offline](#instrument-shows-offline). While the instrument is **Restarting** they stay on, and the request waits for the watcher
- Files read **Not uploaded** until someone requests them, or **Waiting to upload** while an auto-mode watcher (1.4.5 and later) is about to send them
- A file that reads **Upload failed** is one the watcher gave up on. Hover over its status for the reason; see [A file reads Upload failed](#a-file-reads-upload-failed)
- Check the log for `upload_failed`
- A `state_write_failed` event in the watcher’s event log means the PC’s disk is full or the watcher’s state file can’t be written. Free up space; the watcher retries on its own and uploads the files once it can write again
- A revoked or expired token surfaces as `401 Unauthorized`. Create a new token and re-run `init`; see [Issue and revoke tokens](/docs/manage-tokens#after-revoking-a-token)

### A file reads Upload failed [#a-file-reads-upload-failed]

Watcher 1.4.5 and later mark a file **Upload failed** when they give up on it, and the watcher’s activity shows one **Couldn’t upload** entry per run and reason. Hover over the file’s status for the reason:

- **The folder is no longer on the instrument PC.** The run folder was renamed or moved after the watcher found it. The watcher reports the folder under its new name as a new run, so check for a run with the same start time and a similar name: its files are usually already uploaded, and you can dismiss the old ones.
- **The file isn’t on the instrument PC.** The file was moved or deleted. Put it back and choose **Upload**, or choose **Dismiss**.
- **The upload kept failing.** Usually a network or storage problem. The message shows the last error. Choose **Upload** to try again once it’s fixed.
- **The path is outside the watch folder.** Check the watcher’s **Watch folder** setting.

Older watchers put the file back to **Not uploaded** without a reason, and log a “Queued file missing” and a “Gave up uploading” error for each file instead. See [When an upload fails](/docs/browse-runs#upload-failed).

### A requested upload stays on Uploading

On an instrument in **auto** mode, **Request upload** needs watcher 1.2.1 or later. Older watchers in auto mode never read the upload queue, so the file shows **Uploading** and never arrives. Update the watcher; see [Roll out watcher releases](/docs/watcher-releases#what-each-version-adds).

### Files larger than 5 GB don’t upload

Watchers older than 1.2.0 can’t upload files larger than 5 GB, and Data Hub refuses the upload instead of letting it fail partway. Update the watcher to 1.2.0 or later, which uploads large files in parts.

### An upload was cut off by a restart or an update [#an-upload-was-cut-off-by-a-restart-or-an-update]

Watcher 1.2.1 and later retry an automatic upload that didn’t finish the next time the watcher starts, on up to three starts. Two events tell you when it stops trying:

- `upload_retries_exhausted`: the upload still failed after three starts. Choose **Upload** on the file’s run page to try again.
- `pending_upload_missing`: the file was no longer on disk when the watcher started, so there was nothing to retry.

From watcher 1.4.5, the file reads **Upload failed** as soon as an automatic upload fails, with the reason on the file instead of these events, and the watcher still retries it on its next starts. Older watchers don’t retry; use **Upload** on the run page instead.

### A file stays on Waiting to upload after the watcher restarted [#a-file-stays-pending-after-the-watcher-restarted]

Watchers before 1.4.1 could lose track of a file in an automatic upload when the watcher stopped without shutting down cleanly, such as after a reboot, a power cut, or a crash, just after it reported the run. The run is in Data Hub, but the file reads **Not uploaded** and nothing uploads it, because after the restart the watcher treats the file as already handled. Watcher 1.4.1 and later record a run and its files on the PC together, so a restart like that doesn’t leave a file behind.

Updating doesn’t pick up files that an older watcher already lost this way. Ask for them from the run page:

<Steps>

<Step>
If the watcher is older than 1.2.1, update it first. Older watchers in auto mode ignore upload requests; see [A requested upload stays on Uploading](#a-requested-upload-stays-on-uploading).
</Step>

<Step>
Open the run, select the files that read **Not uploaded**, and choose **Upload**. To ask for the files of several runs at once, select the runs in the run list and choose **Upload**. See [Request an upload](/docs/browse-runs#request-upload).
</Step>

<Step>
The watcher picks up the request within a minute and uploads the files that are still on the instrument PC.
</Step>
</Steps>

### Files with the same name were skipped [#files-with-the-same-name-were-skipped]

When a run gathers files from several folders, watchers older than 1.1.0 uploaded only the first file with a given name and skipped the rest. Watcher 1.1.0 and later keep every copy, adding a short tag to later names. To upload files an older watcher skipped:

<Steps>

<Step>
Update the watcher to 1.1.0 or later.
</Step>

<Step>
Stop the watcher (`data-hub-watcher service stop`, or `Ctrl+C` in the foreground).
</Step>

<Step>
Run `data-hub-watcher state forget --prefix your_folder_name/` on the instrument PC, where `your_folder_name/` is the folder under the watch directory that held the skipped files.
</Step>

<Step>
Start the watcher again. It reports the files in that folder again and uploads the ones Data Hub doesn’t have. A run that was deleted on Data Hub refuses its files instead. See [A run was deleted on Data Hub](#a-run-was-deleted-on-data-hub).
</Step>

</Steps>

## Auto-update never fires

Check, in order:

- Prefer a long-running service (or scheduled) install; a one-off console session may not stay up for the hourly tick
- Environment is not `preview`: auto-update is hard-disabled there
- Activity-window guard is not holding it up: run `data-hub-watcher self-update`, or ask an admin to flag the release **mandatory**
- **Last heartbeat** on the watcher’s page is recent; a stale watcher is not ticking

Upgrade failure modes (`update_started` → `update_failed`, editable installs, missing Scheduled Task) are covered in [Install and update the watcher](/docs/install-the-watcher#manual-update-self-update) and [Roll out watcher releases](/docs/watcher-releases).

## Windows service

### The service exits immediately

A config file that doesn't load (missing, unreadable, not saved as UTF-8, malformed, or with a value the watcher doesn't accept) stops the service. `watcher.log` has an error that starts with `Cannot load config`, followed by the reason. The error also gives the command that checks the file, in the form `data-hub-watcher --config "C:\path\to\config.yaml" config validate`. Run it as written, because without `--config` it checks the config file of whoever runs it, not the one the service uses. Fix what it reports and start the service again.

An env file that isn't saved as UTF-8 stops the service the same way, with an error that starts with `Cannot load env file`. Windows PowerShell 5.1 writes UTF-16 for `>` and `>>`, so `echo X=Y >> .env.production` breaks a UTF-8 env file. Watchers before 1.4.2 wrote only a traceback to the Application event log for either problem.

If it stops before writing to `watcher.log`:

- Check `C:\ProgramData\DataHubWatcher\service-bootstrap.log` for a pre-dispatcher crash (missing `pywin32`, moved venv, corrupt install)
- Query the Windows Application event log:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Application'; StartTime=(Get-Date).AddHours(-1)} |
  Where-Object { $_.ProviderName -match 'Python|DataHubWatcher' -or $_.Message -match 'DataHubWatcher' } |
  Format-List TimeCreated, ProviderName, Id, LevelDisplayName, Message
```

- Run the service in the foreground to see the traceback:

```powershell
& "C:\path\to\venv\Scripts\python.exe" -m win32serviceutil debug DataHubWatcher
```

### `self-update` says “Upgrade dispatched” but nothing happens

On Windows uv-tool installs, the upgrade runs out of process under SYSTEM and takes 30–60s. Track it:

```powershell
Get-Service data-hub-watcher
Get-Content ~/.data-hub/upgrade-worker.log -Tail 20 -Wait
```

### Turn on debug logging for the service

Add `DATA_HUB_WATCHER_LOG_LEVEL=DEBUG` to the env file the service loads (typically `~/.data-hub/.env.<environment>`) and restart the service. No reinstall needed. This works with watcher 1.4.2 and later; earlier versions ignore the setting in the env file.

## Where are the logs?

Rotating logs (10 MB each, 5 backups). CLI `watch` and the Windows service share one file:

| Platform | Log file |
| --- | --- |
| Windows | `C:\ProgramData\DataHubWatcher\watcher.log` |
| macOS / Linux | `~/.data-hub/watcher.log` |

Add `--verbose` for debug console output: `data-hub-watcher --verbose watch`. Windows uv-tool upgrade output lands in `~/.data-hub/upgrade-worker.log`.

## API clients get `401 Unauthorized`

The bearer token is missing, mistyped, revoked, or expired. Check **Settings → Access Tokens** and re-issue if needed. See [Issue and revoke tokens](/docs/manage-tokens).

A script that calls the watcher or processing routes with a browser session, instead of a token, also gets `401`. Those routes accept only personal access tokens; see [How a token acts](/docs/manage-tokens#how-a-token-acts).

## MCP clients get `401 Unauthorized`

MCP doesn’t accept personal access tokens, so a client configured with `Authorization: Bearer dhub_…` gets a 401 on every call. Remove the header, leave only the URL, and let the client run its sign-in flow. Setup per client is in [MCP overview](/docs/mcp#connect-a-client).

An already-connected client that starts failing has usually lost its grant: sign in again from the client. If reads work and one tool fails with a missing-scope message, the client holds `read` but not `write`; reconnect and approve both.
