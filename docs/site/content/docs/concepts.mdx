Short definitions of the words these docs use, grouped by what they describe: the equipment, the data, the rules that turn files into runs, and who can do what.

## Instruments and watchers [#equipment-and-fleet]

### Instrument [#instrument]

A piece of lab equipment registered in Data Hub. Each instrument has an **instrument ID** made of lowercase words joined by hyphens, such as `akta-fplc` or `plate-sealer-a`, and a display name for people to read. The ID can’t change, because Data Hub uses it in the storage path of every file and to identify the instrument everywhere else.

An instrument has three states. The **Instruments** page groups them into a tab per state, and a status badge beside each name shows whether new files can reach Data Hub:

| State      | Shown as                                        | Meaning                                                             |
| ---------- | ----------------------------------------------- | ------------------------------------------------------------------- |
| `pending`  | **Pending** tab, with a **Pending** badge       | Registered but not yet confirmed by an admin. A watcher can’t upload for it. |
| `active`   | **Active** tab, with an **Online**, **Restarting**, **Connecting**, or **Offline** badge | Confirmed and accepting uploads.                                    |
| `inactive` | **Retired** tab, with a **Retired** badge       | Deactivated. No longer accepting uploads, but its runs stay browsable. |

See [Set up an instrument](/docs/set-up-an-instrument), [Manage instruments](/docs/manage-instruments), and [Retire an instrument](/docs/retire-an-instrument).

### Instrument type [#instrument-type]

Separate from the instrument ID. The type tells Data Hub which [processor](#preprocessor) reads files from this instrument, so it decides what metadata, badges, and reports you get.

Admins set it from the instrument page: open the three-dot menu, choose **Edit details**, and pick a supported type. An instrument with no matching type still stores and serves raw files. It gets no extracted metadata and no processed files. See [Instrument data preprocessing](/docs/instrument-preprocessing).

### Instrument status [#instrument-status]

The badge beside an instrument’s name, in the instruments table, on Home, and in search results. It answers one question: will new files from this instrument show up? It’s meant for the people who use the instrument, so it leaves out the watcher’s details.

Hover over the badge, or focus it with the keyboard, for a one-sentence explanation. On an instrument’s page and in the instruments table, select the badge to open the instrument’s [watcher page](/docs/manage-watchers#the-watcher-page). In search results the whole row is the link, so the badge there is only a label.

| Badge | When it shows | What it means |
| ----- | ------------- | ------------- |
| **Pending** | The instrument isn’t confirmed yet. This wins over everything below, even when its watcher is checking in. | Waiting for an admin to confirm this instrument. |
| **Retired** | The instrument is retired. This wins over the watcher’s state. | This instrument no longer takes new runs. Its runs stay browsable. |
| **Connecting** | The watcher registered but hasn’t sent its first heartbeat, and 15 minutes haven’t passed since it registered or since an admin confirmed the instrument, whichever came later. | The watcher was set up recently and hasn’t checked in yet. |
| **Restarting** | The watcher stopped for a Windows restart or an automatic update less than 15 minutes ago. | The instrument PC is restarting or the watcher is updating. Either takes a minute or two. |
| **Online** | The watcher is watching and its last heartbeat is less than 5 minutes old. | New files upload automatically, or when someone requests them if the instrument is in manual upload mode. |
| **Offline** | Anything else: the instrument has no watcher, or its watcher was deregistered; the watcher is silent, never checked in, stopped by someone, or can’t find its watch folder. | New files won’t appear right now. A notice on the instrument page says why. |

Only the watcher’s own state decides **Online**, **Restarting**, **Connecting**, and **Offline**. A pending change to the watcher’s settings never changes the badge. An instrument that is **Offline** shows a notice with the reason; see [Check that new files will arrive](/docs/browse-runs#check-files-will-arrive). If it stays **Offline** for 30 minutes, people who subscribe to it are notified; see [When an instrument goes offline](/docs/configure-notifications#instrument-offline).

### Watcher [#watcher]

The `data-hub-watcher` command-line program that runs on an instrument PC. It watches a folder, groups new files into runs, uploads them to cloud storage, and checks in with Data Hub every minute. Each instrument can have at most one active watcher at a time.

Each watcher registers with Data Hub and gets a registration ID for each [environment](#environment) it connects to. Each instrument’s watcher has its own page, under the instrument, with its activity, health, and settings. Deregistering a watcher is a [soft delete](#soft-delete): the instrument keeps it as a past watcher, and its history stays visible for auditing. See [Manage the watcher fleet](/docs/manage-watchers).

### Watcher status [#watcher-status]

The state a watcher’s page shows, and **Settings → Watchers** shows for admins, worked out from the watcher’s most recent [heartbeat](#heartbeat):

| Status | Meaning |
| --- | --- |
| **Online** | A heartbeat arrived in the last 5 minutes. |
| **Unresponsive** | No heartbeat for more than 5 minutes: the process crashed, the PC is off, or the network is blocking Data Hub. A watcher that stopped for a Windows restart, a shutdown, or an automatic update gets 15 minutes instead. So does a new watcher that never sent a heartbeat, counted from when it registered or its instrument was confirmed; hovering over its badge says it never checked in. |
| **Stopped** | The watcher shut down cleanly and said so in its last heartbeat. A stop you chose, such as `data-hub-watcher service stop`, shows **Stopped** until the watcher starts again. A stop for a Windows restart, a shutdown, or an automatic update shows **Stopped** for 15 minutes, then **Unresponsive** if the watcher hasn’t returned. |
| **Waiting: folder not found** | The watcher is running and checking in, but its watch folder is missing, so it isn’t watching anything. It starts watching again once the folder is back. Watchers before 1.4.3 notice a missing folder only when they start. |
| **Registered** | The watcher registered but hasn’t sent its first heartbeat. It turns **Unresponsive** 15 minutes after it registered, or after an admin confirmed its instrument if that came later. It stays **Registered** while its instrument is pending, because the watcher doesn’t start until the instrument is confirmed. |
| **Deregistered** | A past watcher. Someone deregistered it, or retired its instrument. Its page is read-only. |

Hover over a **Stopped** badge to see when it turns **Unresponsive** if the watcher doesn’t return. Watchers before 1.4.1 don’t tell Data Hub about a Windows restart, and watchers before 1.4.2 don’t mark a stop for an automatic update, so Data Hub doesn’t expect those watchers back.

An unresponsive watcher keeps its registration and history, so you can read its last events to work out what happened. See [Troubleshoot a watcher](/docs/troubleshoot-a-watcher).

Instruments show a simpler summary of this status, the [instrument status](#instrument-status) badge. An instrument has one active watcher, so the badge follows that watcher; an instrument with no active watcher reads **Offline**.

### Heartbeat [#heartbeat]

The check-in a watcher sends to Data Hub every 60 seconds. It reports the watcher’s version, instrument ID, watch folder, upload mode, upload counts, and how long it has been running. Data Hub uses it for **Last heartbeat** on the watcher’s page, the status badges, and the connectivity grid on the **Health** tab.

The same loop runs the hourly update check. The watcher checks for requested uploads separately, also once a minute, so a slow upload can’t delay a heartbeat. If a heartbeat fails to send, watcher 1.4.3 and later add its counts to the next one.

### Events [#events]

A watcher’s log of what it did and what went wrong, such as `watcher_started`, `run_reported`, `file_uploaded`, `update_succeeded`, and `error`. The watcher sends its events with each heartbeat. The watcher’s **Activity** tab shows them with a plain label and message, so you can see what happened on the PC without going to it. Data Hub records some events itself, such as `upload_requests_cancelled` when someone deletes a run that had requested uploads.

With watcher 1.4.3 and later, events that couldn’t be sent are kept on the PC and sent later with their original time, and an `events_dropped` event counts any that were lost. See [Activity](/docs/manage-watchers#activity) and [Troubleshoot a watcher](/docs/troubleshoot-a-watcher).

### Environment [#environment]

Which Data Hub deployment a watcher talks to: `staging`, `production`, or `preview`. A `preview` is a Vercel preview deployment, and you give the watcher its API URL by hand. Each environment has its own database, so one PC keeps a separate registration and local records for each environment and can switch between them.

## Data [#data]

### Run [#run]

The files from one acquisition, grouped together. The watcher gives each file a **run ID** using its [run detection](#run-detection) rule, then reports the run to Data Hub. The first file creates the run, and later files with the same run ID join it. Spaces at the start or end of a run ID are ignored, so `RUN001` with a space after it is the same run as `RUN001`.

### Run status [#run-status]

How far a run’s files have got from the instrument to the web app. From the most urgent down, a run shows **Failed**, **Stalled**, **Upload failed**, **Waiting to upload**, **Uploaded**, **Queued**, **Processing**, **Not uploaded**, **Completed**, or **Empty**. When a run’s files are in different states, the run shows the first of these that applies.

Filter by status under **Add filter** on any run list. [What each run status means](/docs/browse-runs#run-status) explains each one.

### File and file category [#file-and-file-category]

Every file in a run has a category, shown as a label in the run’s files table:

- **Raw**: what the instrument wrote, uploaded unchanged
- **Processed**: what a [processor](#preprocessor) made from a raw file, such as a CSV of well values, a contrast-adjusted PNG, or a preview JPG

Both categories download the same way, and file filters on the run page work on this label. See [Download files](/docs/browse-runs#download-files).

### Processor [#preprocessor]

The server-side code that reads a raw file, extracts metadata, and writes processed files. It runs in an AWS Lambda when a file arrives in raw storage, or when you choose **Reprocess**. Reprocessing starts at most 10 files at a time and queues the rest; see [How reprocessing is queued](/docs/browse-runs#reprocess-queue). Which processor runs depends on the [instrument type](#instrument-type), and not every type has one. Per-type inputs and outputs are in [Instrument data preprocessing](/docs/instrument-preprocessing).

### Run archive [#run-archive]

The zip that **Download all** builds for a run. It covers the run’s active files and respects any file filter you have applied. Large archives build in the background as an archive job, so the first request can return a wait time rather than a file.

### Attribution [#attribution]

The record of who ran a run. Choose **Claim** on a run to put your name on it. You can only claim runs for yourself, and API tokens can’t claim runs. Claims fill **My runs** and the “ran by” filters, and claiming a run subscribes you to its comments. See [Claim who ran it](/docs/browse-runs#claim-who-ran-it).

### Lab notebook [#lab-notebook]

A Data Hub record that stands for one notebook page, such as a Notion or Google Docs page. It has a name, an optional description and owner, and the runs added to it from any instrument. A run can be in several lab notebooks, and anyone signed in can create lab notebooks and add or remove runs. See [Lab notebooks](/docs/lab-notebooks).

## Turning files into runs [#turning-files-into-runs]

### Run detection [#run-detection]

The rule that gives each file a run ID. There are two kinds:

- **Prefix**: a pattern (a regular expression) picks the run ID out of the file name. The default `^([^_]+)` takes everything before the first underscore, so `RUN001_data.csv` → `RUN001`
- **Directory**: each folder inside the watch folder is its own run, so `RUN001/data.csv` → `RUN001`

The full set of presets, and how to write your own pattern, is in the [Configuration reference](/docs/configuration-reference#run-detection).

### Stability period [#stability-period]

How many seconds a file must stay unchanged, with the same size and modification time, before the watcher treats it as fully written and ready to upload. The default is 5 seconds; raise it for instruments that write large files slowly. [Wait until writes finish](/docs/configure-run-detection#wait-until-writes-finish) covers files that keep changing or that the instrument keeps open.

### Upload mode [#upload-mode]

How files get from the instrument to cloud storage:

- **auto**: files upload as soon as they’re found and stable. The watcher also uploads files someone requests from the run page
- **manual**: the watcher reports runs but uploads a file only after someone requests it in the web app. It checks for requests once a minute. Use this when someone must approve which files leave the instrument PC

### Initial scan [#initial-scan]

What the watcher does with files already in the watch folder the first time it connects to an environment. In `production` it uploads them (`full`). In `staging` and `preview` it records them and skips them (`new-only`), so test environments don’t fill up with old files. See the [Configuration reference](/docs/configuration-reference#initial-scan).

### Dismiss [#dismiss]

Dismissing a file that the watcher found but didn’t upload, or one whose upload failed, tells the watcher not to upload it. A dismissed file stays dismissed, even if the watcher reports it again. Dismissing differs from deleting: the file never reached Data Hub storage, so there’s nothing to restore.

[Approve or dismiss files](/docs/manage-watchers#approving-manual-uploads) explains how, and when a new file at the same path shows up again.

### Soft delete [#soft-delete]

Data Hub marks things deleted instead of erasing them, so their history stays for auditing. Deleting a run hides it from run lists without removing its stored files, and **Show deleted runs** brings it back into view. It also cancels any uploads that were requested for the run’s files, and restoring the run doesn’t bring them back. Deregistering a watcher keeps its events and heartbeats. Anyone signed in can restore a deleted run from the run page.

## People and access [#people-and-access]

### Role [#role]

Data Hub has two roles, **Member** and **Admin**. Members sign in, browse instruments and runs, claim and comment on runs, send feedback, and read the token list. Admins can also confirm and update instruments, create and revoke tokens, promote or demote other users, delete any comment, review feedback, and manage integrations. Full permission tables are in [Security and permissions](/docs/security#roles).

### Personal access token [#personal-access-token]

A secret starting with `dhub_` that the watcher and scripts send to sign in to the Data Hub API. Each token has permission [scopes](#scope), and only admins create and revoke tokens. Data Hub shows the full token once, when it’s created.

A token acts as itself, under its own name. Comments it posts and runs it deletes show the token’s name with a key icon, not a person. Because a token isn’t a person, it can’t claim runs or send feedback. See [Issue and revoke tokens](/docs/manage-tokens).

### Scope [#scope]

A permission a token has, such as `runs:read`. Data Hub refuses a token’s request with `403 FORBIDDEN` when the token lacks the scope that request needs. People signed in to the web app have every scope, so scopes only limit tokens. The scope table is in [Security and permissions](/docs/security#token-scopes).

### Feedback report [#feedback-report]

A bug report or feature request about Data Hub itself, sent from the account menu or by an AI assistant. Each report is stored as an issue in your workspace’s Linear, and its status (Open, Resolved, or Declined) follows that issue. See [Send feedback and see what’s new](/docs/send-feedback).
